# B-hydra secure на C++

Нативная реализация **того же** шифрованного транспорта, что в
`b_hydra/secure.py`. Не новый протокол и не OpenSSL-TLS: это второй
независимый код для одной спецификации.

| Файл | Что внутри |
|---|---|
| `bhydra_hash.hpp` | SHA-512, SHAKE-256 (Keccak-f[1600]), HMAC-SHA512 — с нуля |
| `bhydra_ec.hpp` | 256-битная арифметика, secp256k1 (координаты Якоби), ECDSA + RFC 6979 |
| `bhydra_secure.hpp` | рукопожатие ECDH, вывод ключей, кадры, кадрирование сообщений |
| `bhydra_bridge.cpp` | CLI: мост для pytest + живой клиент/сервер |

Зависимостей нет — только стандартная библиотека C++17 и POSIX-сокеты.
Заголовки самодостаточны: `#include "bhydra_secure.hpp"` и всё.

## Сборка

```bash
g++ -O2 -std=c++17 -pthread -I cpp -o bhydra_bridge cpp/bhydra_bridge.cpp
./bhydra_bridge selftest          # контрольные векторы
```

## Зачем это нужно

**Скорость.** Рукопожатие — это открытый ключ: два умножения точки плюс
подпись или проверка. На чистом Python это десятки миллисекунд.

| Операция | Python | C++ | |
|---|---|---|---|
| умножение точки | 7,8 мс | **0,32 мс** | 24× |
| подпись (RFC 6979) | 12,4 мс | **0,32 мс** | 39× |
| проверка подписи | 14,6 мс | **0,57 мс** | 26× |
| рукопожатие целиком | 65 мс | **2,2 мс** | 29× |
| поток шифра, 4 МиБ | **42 мс** | 91 мс | Python в 2,2× быстрее |

Последняя строка — не опечатка. Поток у Python считает `hashlib.shake_256`,
то есть оптимизированный C внутри интерпретатора; обогнать его простым
переносом на C++ не получилось. Выигрыш C++ там, где Python считает
арифметику САМ, — на кривой.

**Вторая реализация как проверка.** Пока код один, «спецификация» — это то,
что делает Python. Второй независимый код на другом языке заставляет протокол
быть описанным, и любое расхождение видно сразу. Ровно так сделана браузерная
подпись (`bhydra-sign.js`) — и именно там этот приём нашёл настоящую ошибку
вывода нонса, при которой подписи оставались валидными.

**Клиенты вне Python.** Нативный клиент говорит с настоящим узлом:

```bash
./bhydra_bridge connect 127.0.0.1 5000 <ключ_узла_hex> '{"type": "ping"}'
# peer 04…
# {"type": "pong"}
```

## Сверка с Python

`tests/test_cpp_secure.py` сравнивает БАЙТЫ, а не «работает ли»: хеши, общий
секрет ECDH, подписи (они воспроизводимы благодаря RFC 6979), выведенные ключи
сессии, целые кадры — плюс живое рукопожатие через сокет в обе стороны и
запрос к настоящему `P2PNode`. Тесты пропускаются, если компилятора нет.

```bash
python -m pytest tests/test_cpp_secure.py -q
```

## Чего здесь нет

- Названия «TLS» в стандартном смысле: это не RFC 8446, сертификатов и
  удостоверяющих центров нет. Доверие берётся из первого контакта (TOFU).
- Аутентификации клиента — как и в Python-версии.
- Windows: сокеты через POSIX, для winsock нужен свой слой (крипта
  переносима как есть).
- Защиты от атак по времени в арифметике кривой: умножение точки идёт
  простым «удвоить и прибавить», без маскировки. Для долговременного ключа
  УЗЛА на своей машине это приемлемо, для ключей кошелька на чужом
  железе — нет.
