# B-hydra secure на C++

Нативная реализация **того же** шифрованного транспорта, что в
`b_hydra/secure.py`. Не новый протокол и не OpenSSL-TLS: это второй
независимый код для одной спецификации.

| Файл | Что внутри |
|---|---|
| `bhydra_hash.hpp` | SHA-256, SHA-512, SHAKE-256 (Keccak-f[1600]), HMAC-SHA512 — с нуля |
| `bhydra_ec.hpp` | 256-битная арифметика, secp256k1 (координаты Якоби), ECDSA + RFC 6979 |
| `bhydra_secure.hpp` | рукопожатие ECDH, вывод ключей, кадры, кадрирование сообщений |
| `bhydra_bridge.cpp` | CLI: мост для pytest + живой клиент/сервер |
| `bhydra_miner.cpp` | майнер: перебор nonce на всех ядрах — см. ниже |
| `bhydra_ec_lib.cpp` | проверка подписи для Python (.so/.dll) — см. ниже |
| `bhydra_xmss.hpp` | лист дерева XMSS: ключ WOTS из seed — см. ниже |
| `bhydra_xmss_lib.cpp` | генерация листьев XMSS на всех ядрах (.so/.dll) |
| `bhydra_bt.cpp` | Bluetooth под Linux: поиск устройств (BlueZ) — см. ниже |
| `bhydra_bt_win.cpp` | Bluetooth под Windows: ВЕСЬ транспорт + поиск (Winsock) |

Зависимостей нет — только стандартная библиотека C++17 и POSIX-сокеты.
Заголовки самодостаточны: `#include "bhydra_secure.hpp"` и всё.

## Сборка

```bash
g++ -O2 -std=c++17 -pthread -I cpp -o bhydra_bridge cpp/bhydra_bridge.cpp
./bhydra_bridge selftest          # контрольные векторы
```

## Зачем это нужно

**Скорость.** Рукопожатие — это открытый ключ: два умножения точки плюс
подпись или проверка. На чистом Python это десятки миллисекунд.

| Операция | Python | C++ | |
|---|---|---|---|
| умножение точки | 7,8 мс | **0,32 мс** | 24× |
| подпись (RFC 6979) | 12,4 мс | **0,32 мс** | 39× |
| проверка подписи | 14,6 мс | **0,57 мс** | 26× |
| рукопожатие целиком | 65 мс | **2,2 мс** | 29× |
| поток шифра, 4 МиБ | **42 мс** | 91 мс | Python в 2,2× быстрее |

Последняя строка — не опечатка. Поток у Python считает `hashlib.shake_256`,
то есть оптимизированный C внутри интерпретатора; обогнать его простым
переносом на C++ не получилось. Выигрыш C++ там, где Python считает
арифметику САМ, — на кривой.

**Вторая реализация как проверка.** Пока код один, «спецификация» — это то,
что делает Python. Второй независимый код на другом языке заставляет протокол
быть описанным, и любое расхождение видно сразу. Ровно так сделана браузерная
подпись (`bhydra-sign.js`) — и именно там этот приём нашёл настоящую ошибку
вывода нонса, при которой подписи оставались валидными.

**Клиенты вне Python.** Нативный клиент говорит с настоящим узлом:

```bash
./bhydra_bridge connect 127.0.0.1 5000 <ключ_узла_hex> '{"type": "ping"}'
# peer 04…
# {"type": "pong"}
```

## Сверка с Python

`tests/test_cpp_secure.py` сравнивает БАЙТЫ, а не «работает ли»: хеши, общий
секрет ECDH, подписи (они воспроизводимы благодаря RFC 6979), выведенные ключи
сессии, целые кадры — плюс живое рукопожатие через сокет в обе стороны и
запрос к настоящему `P2PNode`. Тесты пропускаются, если компилятора нет.

```bash
python -m pytest tests/test_cpp_secure.py -q
```

## Чего здесь нет

- Названия «TLS» в стандартном смысле: это не RFC 8446, сертификатов и
  удостоверяющих центров нет. Доверие берётся из первого контакта (TOFU).
- Аутентификации клиента — как и в Python-версии.
- Windows: сокеты через POSIX, для winsock нужен свой слой (крипта
  переносима как есть).
- Защиты от атак по времени в арифметике кривой: умножение точки идёт
  простым «удвоить и прибавить», без маскировки. Для долговременного ключа
  УЗЛА на своей машине это приемлемо, для ключей кошелька на чужом
  железе — нет.

# Bluetooth: `bhydra_bt.cpp`

Отдельный слой и с другой целью. `bhydra_secure.hpp` существует ради
**скорости** — там C++ ускоряет кривую в 29 раз. Здесь скорость ни при чём:
системный вызов быстрее от языка не станет. Здесь C++ нужен потому, что
нужного **нет в Python вообще**.

| Что | Где живёт | Почему |
|---|---|---|
| соединение по RFCOMM | Python (`transport.py`) | `AF_BLUETOOTH`/`BTPROTO_RFCOMM` есть в stdlib |
| поиск устройств вокруг | **C++** (`bhydra_bt.cpp`) | `hci_inquiry` — только C API BlueZ |

Поиск и делает связь D2D: узлы находят друг друга там, где нет ни роутера, ни
интернета, ни общего адресного пространства. У TCP эту роль играет UDP-маяк, а
у Bluetooth — обзор эфира.

## Сборка

```bash
sudo apt-get install libbluetooth-dev            # заголовки BlueZ
g++ -O2 -std=c++17 -o bhydra_bt cpp/bhydra_bt.cpp -lbluetooth
./bhydra_bt selftest        # {"ok": true, "channel": 5, "bdaddr_size": 6}
./bhydra_bt adapter         # свой адрес и имя
./bhydra_bt scan 6          # устройства поблизости, JSON
```

Python находит слой по имени `bhydra_bt` в PATH или по переменной
`BHYDRA_BT_BRIDGE`. Не собран — транспорт всё равно работает, просто соседей
придётся называть по адресу вручную.

## Запуск узла по Bluetooth

```bash
python -m b_hydra.p2p --port 5 --transport bluetooth
```

`--port` здесь — **канал RFCOMM** (их всего 30), и он играет ту же роль, что
порт 5000 у TCP: обе стороны обязаны знать одно число заранее. Константа одна
на два языка (`BLUETOOTH_CHANNEL` в Python, `kRfcommChannel` в C++), и тест
`test_native_layer_agrees_with_python_about_the_channel` следит, чтобы они не
разъехались: иначе узлы слушали бы и звонили на разные каналы и молча никогда
не встретились.

## Чего здесь нет

- **SDP** (объявить сервис и спросить у соседа номер канала). Поэтому канал
  фиксированный. SDP — это ещё около сотни строк, а проверить их здесь НЕЧЕМ:
  адаптера в контейнере нет. Непроверенный код в этот проект не заводят.
- **Отбора «своих» при поиске.** `scan` возвращает всё видимое — наушники и
  телефоны тоже. Отсеивает их рукопожатие B-hydra, где сверяется отпечаток
  сети; UDP-маяк устроен ровно так же.
- **Windows и macOS**: BlueZ — это Linux. На Android Bluetooth доступен только
  из Java (в NDK публичного API нет), поэтому C++ там не поможет.

## ⚠️ Что НЕ проверено

**Передача по воздуху.** В окружении, где это написано, нет адаптера
Bluetooth: `AF_BLUETOOTH` отвечает «Address family not supported». Проверено
всё остальное — сборка без предупреждений, контрольные векторы (разбор
адресов, порядок байтов `bdaddr`, экранирование JSON), поведение БЕЗ железа
(понятная ошибка в JSON вместо падения), разбор ответов на стороне Python и
логика поиска соседей на подменённом транспорте. Тесты с живым адаптером
написаны и включатся сами на машине, где он есть.

# Bluetooth под Windows: `bhydra_bt_win.cpp`

Отдельный файл, а не `#ifdef`: общего кода с Linux-версией нет вовсе. У Linux
это BlueZ (`hci_inquiry`, `bdaddr_t`, сокеты `AF_BLUETOOTH`), у Windows —
Winsock (`AF_BTH`, `SOCKADDR_BTH`) и `bluetoothapis.h`. Совпадает только смысл
операций, а не их вид.

## Почему здесь ВЕСЬ транспорт, а не только поиск

| | Linux | Windows |
|---|---|---|
| соединение RFCOMM | Python (`AF_BLUETOOTH` в stdlib) | **C++** — у Python таких сокетов нет |
| поиск устройств | **C++** (`hci_inquiry`) | **C++** (`BluetoothFindFirstDevice`) |

Модуль `socket` в CPython не умеет разбирать `SOCKADDR_BTH` ни в каком виде, и
обойти это из Python нельзя. Поэтому на Windows нативно всё: открыть, принять,
прочитать, записать. Python получает объект, похожий на сокет (обёртка над
дескриптором через ctypes), и выше по стеку никто не замечает разницы — стеку
нужны ровно `sendall`, `recv`, `settimeout`, `gettimeout`, `shutdown`, `close`.

## Сборка (кросс-компиляция с Linux)

```bash
sudo apt-get install mingw-w64
x86_64-w64-mingw32-g++ -O2 -std=c++17 -static -o bhydra_bt.exe \
    cpp/bhydra_bt_win.cpp -lws2_32 -lbthprops
x86_64-w64-mingw32-g++ -O2 -std=c++17 -static -shared -DBHYDRA_BT_DLL \
    -o bhydra_bt.dll cpp/bhydra_bt_win.cpp -lws2_32 -lbthprops
```

На самой Windows тем же mingw-w64 или MSVC (`ws2_32.lib`, `bthprops.lib`).

Два артефакта из одного исходника:

* **`bhydra_bt.exe`** — те же команды, что у Linux-слоя (`selftest`, `adapter`,
  `scan`), и тот же JSON. Поэтому поиск соседей в Python — общий код на обеих
  системах (`WindowsBluetoothTransport` наследует `scan`/`neighbours` без
  изменений).
* **`bhydra_bt.dll`** — функции транспорта для ctypes. Путь задаётся
  переменной `BHYDRA_BT_DLL`, файл `bhydra_bt.exe` ищется по `BHYDRA_BT_BRIDGE`.

## Запуск

```powershell
python -m b_hydra.p2p --port 5 --transport bluetooth
```

Транспорт выбирается по системе автоматически (`transport.bluetooth_transport`).

## ⚠️ Что проверено, а что нет

Проверено **без Windows-машины и без адаптера**:

* обе сборки идут кросс-компилятором **без единого предупреждения**;
* результат — настоящий PE-бинарник (`MZ` + `PE\0\0`), а не «что-то собралось»;
* `bhydra_bt.exe selftest` **запускается под Wine и проходит**: разбор адресов
  в обе стороны, отказ от шести видов мусорных адресов, экранирование JSON,
  подъём Winsock, `AF_BTH == 32`, `sizeof(SOCKADDR_BTH) == 30`;
* без адаптера (а под Wine его нет) команды отвечают JSON с ошибкой и кодом 1,
  а не падают;
* канал RFCOMM сверяется во всех ТРЁХ местах сразу — Python, Linux-слой,
  Windows-слой.

**НЕ проверено**: передача по воздуху и работа на настоящей Windows. Wine — не
Windows, и Bluetooth-стека в нём нет. Всё, что касается радио, проверит только
владелец двух машин.

# Майнер: `bhydra_miner.cpp`

Перебор nonce — единственное место в проекте, где Python считает САМ и много:
миллионы SHA-512 подряд, и всё в один поток из-за GIL.

```bash
g++ -O2 -std=c++17 -pthread -I cpp -o bhydra_miner cpp/bhydra_miner.cpp
./bhydra_miner selftest        # {"ok": true, "threads": 4}
./bhydra_miner bench 2         # скорость на всех ядрах
```

Python находит его по `BHYDRA_MINER`, затем в `PATH`, затем в корне проекта.
`BHYDRA_MINER=off` выключает. Не собран — майнинг просто идёт на Python.

## Замер (4 ядра)

| путь | хеш/с | |
|---|---:|---|
| Python, чистый SHA (по умолчанию) | 3 023 | |
| Python, `hashlib` | 931 793 | |
| C++, 1 поток | 935 814 | **не быстрее Python** |
| C++, 4 потока | 3 791 693 | ×4,07 к Python |

⚠️ Главный вывод неочевидный: **в один поток C++ не быстрее**. `hashlib` — это
OpenSSL, вылизанный десятилетиями и часто с аппаратными инструкциями; наш
SHA-512, написанный с нуля, с ним ровно вровень. Весь выигрыш нативного
майнера — в ПАРАЛЛЕЛИЗМЕ, которого у Python нет из-за GIL. Против режима по
умолчанию (чистый SHA) разрыв — в 1254 раза, но это сравнение с «всё своё», а
не с оптимизированным C.

## Windows

Тот же исходник, отдельного файла не нужно: здесь только стандартная
библиотека C++ и потоки, а не системные API (в отличие от Bluetooth, где
пришлось писать два разных слоя).

```bash
x86_64-w64-mingw32-g++ -O2 -std=c++17 -static -I cpp \
    -o bhydra_miner.exe cpp/bhydra_miner.cpp
```

Проверено кросс-сборкой без предупреждений и запуском ПОД WINE: `selftest`
проходит, потоки видны, а найденный виндовой сборкой блок пересчитан Python и
принят. На настоящей Windows не запускался.

## Как устроено

Потоки не делят счётчик: поток `i` берёт nonce `start+i`, `start+i+N`, … —
атомарный инкремент на каждый хеш съел бы весь выигрыш. Внутри — тот же
midstate, что и в Python: неизменная часть заголовка сжимается один раз
(`Sha512` копируемый), сравнение идёт по 64 байтам, а не переводом хеша в
число.

Работает **срезами по времени**: Python просит «поищи секунду», получает
результат и решает, продолжать ли. Отдать управление насовсем нельзя — узел
снова оглох бы на время майнинга и не смог бы бросить блок, когда сосед нашёл
свой раньше.

## Майнеру не верят на слово

Найденный блок ПЕРЕСЧИТЫВАЕТСЯ Python-кодом и сверяется с порогом
(`Block._mine_native`). Соврал — `ValueError`, громко и сразу. Молчаливый
откат на Python здесь был бы хуже: сломанный майнер всплыл бы только как
отвергнутые сетью блоки, и причину искали бы долго. Оба случая закреплены
тестами: и выдуманный хеш, и настоящий хеш, не проходящий порог.

# Проверка подписи: `bhydra_ec_lib.cpp`

Замер приёма одной транзакции: **15,5 мс, из них 12,2 — проверка подписи**.
Хеш там всего 5%, так что ускорять надо кривую, а не SHA.

Считает то же уравнение из `bhydra_ec.hpp`, что обслуживает рукопожатие
транспорта: **чужой криптографии не добавляется**, наш алгоритм просто
скомпилирован. Сторонняя libsecp256k1 (`coincurve`) остаётся необязательным
запасным ускорителем и берётся только если своей библиотеки нет.

```bash
g++ -O2 -std=c++17 -shared -fPIC -I cpp -o libbhydra_ec.so cpp/bhydra_ec_lib.cpp
python -c "from b_hydra import wallet; print(wallet._BACKEND)"
# bhydra_ec (свой C++)
```

Python находит её по `BHYDRA_EC_LIB` или рядом с проектом; `off` выключает.

| | чистый Python | свой C++ |
|---|---:|---:|
| проверка подписи | 12,24 мс | **0,71 мс** (×17) |
| приём транзакции | 15,49 мс | **3,66 мс** (×4,2) |

## Почему библиотека, а не команда

У майнера мост — отдельный процесс, и это правильно: он молотит секундами,
запуск процесса теряется в фоне. Здесь наоборот — работы на полмиллисекунды, и
запуск процесса стоил бы дороже самой проверки. Поэтому `.so`/`.dll` и ctypes:
накладные расходы вызова — микросекунды.

⚠️ У ctypes обязательны `argtypes`: без них указатели уедут, и проверка начнёт
читать не оттуда — молчаливая порча вместо отказа.

## Множество принимаемых подписей обязано СОВПАДАТЬ

Это важнее скорости. Разойдись оно — узлы с собранной библиотекой и без неё
по-разному решали бы, какая транзакция валидна: одни приняли бы блок, другие
отвергли. Раскол сети на ровном месте.

Поэтому здесь повторены все проверки чистого Python (точка на кривой — защита
от invalid-curve, диапазон r и s), а перед включением бэкенда Python прогоняет
self-test на живых подписях, причём **на обеих половинах**: верную подпись
принять И подделку отвергнуть. Ядро, отвечающее «да» на всё, — самая опасная
поломка (узел принимал бы любые чужие траты), и односторонняя проверка его бы
пропустила. Отдельными тестами закреплено, что self-test ловит и «да на всё»,
и «нет на всё».

# Листья XMSS: `bhydra_xmss.hpp`, `bhydra_xmss_lib.cpp`

Пост-квантовая часть проекта (`b_hydra/pqcrypto.py`) держится на XMSS: дерево
Меркла над 2^h одноразовыми ключами WOTS, корень которого и есть публичный
ключ. Обход BDS в своё время сделал подпись дешёвой (O(h) вместо O(2^h)), но
**генерацию удешевить нельзя никаким алгоритмом**: корень стоит над всеми
листьями, значит каждый обязан быть посчитан хотя бы раз.

Один лист — это `len·W + 1` хешей: **1073** в режиме P256 и **2097** в P512.
Дерево высоты 16 — это 70 миллионов хешей.

## Сборка

```bash
g++ -O2 -std=c++17 -pthread -shared -fPIC -I cpp \
    -o libbhydra_xmss.so cpp/bhydra_xmss_lib.cpp
x86_64-w64-mingw32-g++ -O2 -std=c++17 -shared -static -I cpp \
    -o bhydra_xmss.dll cpp/bhydra_xmss_lib.cpp
```

Файл достаточно положить рядом — `native_xmss.py` найдёт его сам.
Выключается переменной `BHYDRA_XMSS_LIB=off`.

## Замер (4 ядра, режим P256, один лист)

| Движок | мс на лист | h=16 | h=20 |
|---|---|---|---|
| наш чистый Python-SHA | 292,23 | 308 мин | 82 ч |
| `hashlib` (OpenSSL) | 0,98 | 1,08 мин | 17,2 мин |
| C++, один поток | **0,39** | 0,42 мин | 6,8 мин |
| C++, три потока | **0,13** | **11 с** | **2,8 мин** |

⚠️ **Вывод здесь ДРУГОЙ, чем у майнера, и это стоит понимать.** У майнера C++ в
один поток оказался вровень с `hashlib`: там один большой хеш за другим, а
`hashlib` — это OpenSSL, и обогнать его своим SHA не выйдет. Здесь же C++ в
один поток быстрее в 2,5 раза, потому что лист — это тысяча **крошечных**
хешей, и время съедает не SHA, а накладные расходы интерпретатора на каждый
вызов. Их нативный код убирает ещё до всякого параллелизма.

⚠️ Четыре потока на четырёх ядрах оказались ХУЖЕ трёх (0,16 против 0,13) —
подтверждение общего с майнером правила «все ядра, кроме одного».

## Почему сюда уехали только ЛИСТЬЯ

Замер: узлы дерева — 0,24–0,34% общего времени, всё остальное листья. Но дело
не только в этом.

Лист — **чистая функция** от `(seed, index)`: у неё нет состояния, и разойтись
двум реализациям негде. Обход BDS — наоборот, код с тонкой семантикой
(расписание treehash, путь включения, перенос состояния с листа на лист), и
второй его копии в проекте быть не должно. Ровно поэтому в своё время
`sign_hash` **вынесли** из `sign`, а не скопировали, и ровно поэтому две
реализации кривой свели в единый `ec.py`.

## SHA-256 появился ради этого

В `bhydra_hash.hpp` SHA-256 не было вовсе: в цепочке B-hydra он не участвует
нигде, там всюду SHA-512. Но режим XMSS по умолчанию (P256) строит цепочки
Винтерница именно на нём, и без него нативным был бы только «параноидальный»
P512.

Заодно у обоих хешей появился `one_shot` — одноразовый путь без единого
выделения памяти. На 70 миллионах коротких хешей `Bytes buffer_` с его
`insert`/`erase` стоит дороже самого сжатия. Это **не вторая реализация**:
`compress` тот же самый, расходятся только подача байтов и дополнение.

## Байты обязаны совпадать — иначе это чужой адрес

Корень дерева — публичный ключ XMSS и часть гибридного адреса (версия `0x2f`).
Ядро, считающее листья хоть немного иначе, дало бы **другой адрес**: монеты
ушли бы туда, откуда их не достанет никто.

Поэтому проверок две, и обе обязательны:

1. **Библиотека проверяет себя** векторами NIST при первом вызове — пустая
   строка, `"abc"` и длина **на границе блока** (55 байт для SHA-256, 111 для
   SHA-512). Граница нужна отдельно: короткое сообщение идёт одним блоком и
   ошибку в дополнении просто не задевает.
2. **Python сверяет листья с чистой реализацией байт в байт**
   (`pqcrypto._selftest_leaves`) и только потом включает бэкенд. Пачка берётся
   **не с нуля** (`start=1`): считай библиотека всегда от нуля, проверка с
   `start=0` этого бы не заметила, а дерево вышло бы из одинаковых листьев —
   то есть поломка выглядела бы как исправность.

Обе проверки закреплены тестами и подтверждены мутацией: ядро, промахнувшееся
на **один бит**, и ядро, игнорирующее смещение, отсеиваются.

⚠️ В отличие от майнера, параллелизм здесь **не имеет права** влиять на
результат. У майнера любой валидный nonce годится, и недетерминированность
намеренная — она же однажды расколола сеть на генезисе. У листа такой свободы
нет вовсе: лист ровно один, и число потоков на него не влияет (закреплено
тестом на 1, 2, 3 и 8 потоках).

## Отказ не роняет генерацию

Библиотеки нет, режим чужой, seed длиннее допустимого, драйвер отвалился
посреди работы — во всех случаях листья досчитывает Python. Уронить генерацию
значило бы потерять кошелёк из-за сбоя ускорителя, без которого всё прекрасно
работает.

Листья берутся **пачками** (`native_xmss.CHUNK`), а не одним вызовом на всё
дерево: генерация h=20 идёт минутами, и между пачками Python снова получает
управление — отсюда отчёт о прогрессе (`MerkleSigner(on_progress=…)`) и
возможность прервать создание кошелька. Та же причина, по которой нативный
майнер работает срезами по времени.
