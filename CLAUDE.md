# B-hydra Core

Учебная P2P-криптовалюта на модели UTXO. Ядро — чистый Python 3.9+ (стандартная
библиотека, ноль обязательных зависимостей); пакеты из `requirements.txt` — только
опциональные ускорители/утилиты (`coincurve`, `qrcode`, `pyinstaller`, …).

## Команды

```bash
pip install pytest                            # единственная dev-зависимость
python -m pytest -q                           # 903 теста + 2 с адаптером Bluetooth
python -m pytest tests/test_node.py -q        # один файл
python -m pytest tests/test_node.py -k mempool -q   # один тест по имени

python -m b_hydra.cli wallet                  # создать кошелёк (адрес + приватный ключ)
python -m b_hydra.cli mine BHY<адрес> --message "i-3ru"   # добыть блок + заметка
python -m b_hydra.cli send <ключ> <адрес> 10 --fee 0.5
python -m b_hydra.cli balance BHY<адрес>      # состояние CLI — bhydra_chain.json
python -m b_hydra.api                         # веб-сервер: http://0.0.0.0:8000
python -m b_hydra.api --tls                   # HTTPS (сертификат создаётся сам)
python -m b_hydra.api --p2p --seed host:5000  # REST + УЗЕЛ СЕТИ в одном процессе
                                              # (без --p2p узел живёт сам по себе)
python bhydra_gui.py                          # десктоп-клиент (tkinter)
python P2P.py --demo                          # демо-сеть из трёх узлов
python P2P.py --port 5000 --seed host:port    # узел в сети (канал шифруется)
python -m b_hydra.secure                      # демо рукопожатия и кадров
python -m b_hydra.p2p --port 5 --transport bluetooth   # узел по Bluetooth (D2D)
python -m b_hydra.apkbuild --out wallet.apk   # APK для Android без SDK (нужен JDK)

g++ -O2 -std=c++17 -shared -fPIC -I cpp -o libbhydra_ec.so cpp/bhydra_ec_lib.cpp
                                              # ×17 на проверке подписи (свой код)
g++ -O2 -std=c++17 -pthread -I cpp -o bhydra_miner cpp/bhydra_miner.cpp
./bhydra_miner bench 2                        # майнер: скорость на всех ядрах
python -m b_hydra.gpu_miner                   # майнинг на видеокарте (OpenCL):
                                              # список устройств, self-test, замер
                                              # собирать нечего — ядро компилирует
                                              # драйвер; BHYDRA_GPU=off выключает
g++ -O2 -std=c++17 -pthread -I cpp -o bhydra_bridge cpp/bhydra_bridge.cpp
./bhydra_bridge selftest                      # нативный транспорт: свои векторы
g++ -O2 -std=c++17 -o bhydra_bt cpp/bhydra_bt.cpp -lbluetooth   # поиск по Bluetooth
./bhydra_bridge connect 127.0.0.1 5000 <ключ_узла> '{"type": "ping"}'
x86_64-w64-mingw32-g++ -O2 -std=c++17 -static -o bhydra_bt.exe \\
    cpp/bhydra_bt_win.cpp -lws2_32 -lbthprops          # Bluetooth для Windows
x86_64-w64-mingw32-g++ -O2 -std=c++17 -static -I cpp \\
    -o bhydra_miner.exe cpp/bhydra_miner.cpp           # майнер для Windows
```

Линтера/форматтера в проекте нет. Сборка `.exe` — `pyinstaller`, см. `BUILD.md`.

Веб: `/` — обозреватель «живой сети» (`explorer.html`), `/wallet` — кошелёк
(`wallet.html`). Обе страницы работают и с API узла, и в демо-режиме офлайн.
Кошелёк подписывает переводы САМ через `bhydra-sign.js` (отдаётся по
`/bhydra-sign.js`): адрес выводится из ключа локально, наружу уходит только
подписанная транзакция. Если скрипт не загрузился — откат на `/api/send`.

**Кошелёк — приложение для телефона (PWA)**: `manifest.webmanifest` + `sw.js`
(оболочка кэшируется, `/api/…` — НИКОГДА) + иконки из `icon.py`. Ставится на
главный экран, открывается без сети, QR адреса считается на устройстве
(`bhydra-qr.js`), сканирование — встроенным `BarcodeDetector`, где он есть.
**APK собирается БЕЗ Android SDK**: `python -m b_hydra.apkbuild`. Оболочка —
`android/` (WebView, крипты внутри нет). Подробности — `android/README.md`.
**Для iPhone — `ios/`** (SwiftUI + WKWebView, крипты тоже нет). ⚠️ `.ipa` здесь
собрать НЕЛЬЗЯ в принципе: подпись обязана восходить к центру Apple, её
проверяет ядро. На iPhone работает PWA; нативное приложение добавляет только
сканирование QR камерой и ссылки `bhydra:`. См. `ios/README.md`.

| `transaction.py` | UTXO: `TxInput`/`TxOutput`/`Transaction`, `TransactionPool` (мемпул) |
| `ec.py` | арифметика кривых, параметризованная кривой: якобиевы координаты, приём Шамира, ECDSA. Таблица: secp256k1, P-256, brainpoolP512r1 |

| `pqcrypto.py` | пост-квантовые хеш-подписи: Lamport, WOTS, XMSS-lite, `QuantumWallet` (экспериментально) |
| `rsa.py` | RSA с нуля: генерация ключей (CRT, λ(n)), OAEP, PSS, PKCS#1 v1.5, DER/PKCS#8/SPKI/PEM (НЕ в консенсусе) |

| `native_miner.py` | мост к `cpp/bhydra_miner.cpp`: перебор nonce на всех ядрах |
| `gpu_miner.py` | мост к `gpu/bhydra_miner.cl`: перебор nonce на видеокарте (OpenCL через ctypes) |
| `native_ec.py` | мост к `cpp/bhydra_ec_lib.cpp`: проверка подписи НАШЕЙ же ECDSA |

| `api.py`, `cli.py`, `gui.py`, `mobile_client.py` | REST/HTTP, CLI, tkinter-GUI, моб. клиент |

Не на Python четыре места, и все — вторые реализации существующих форматов,
без зависимостей. `bhydra-sign.js`: подпись транзакций в браузере (SHA-512, HMAC,
RIPEMD-160, base58, secp256k1, RFC 6979 и сериализация «как в Python»); мост
для тестов — `tests/js_bridge.js`. `bhydra-qr.js`: QR-код на устройстве, порт
`qrcode_gen.py` модуль в модуль. Каталог `cpp/`: нативный шифрованный
транспорт (`bhydra_hash.hpp`, `bhydra_ec.hpp`, `bhydra_secure.hpp`) и мост
`cpp/bhydra_bridge.cpp` — см. `cpp/README.md`. Каталог `gpu/`: ядро
`bhydra_miner.cl` на OpenCL C — перебор nonce на видеокарте, третья реализация
нашего SHA-512, см. `gpu/README.md`. `bhydra-net.js`: сетевой слой
кошелька (несколько узлов, выбор по работе, SPV). Плюс `sw.js` — сервис-воркер
кошелька, `android/` — оболочка WebView и `ios/` — оболочка SwiftUI+WKWebView
(все три без крипты).

Корневые `*.py` (`cli.py`, `api.py`, `P2P.py`, `cache.py`, `IP.py`, …) — тонкие
запускалки/шимы поверх пакета; править логику нужно в `b_hydra/`. Тесты —
`tests/` (42 файла, 907 тестов, `pytest`). Полная карта слоёв — `ARCHITECTURE.md`,
схема REST-подписи — `API.md`.

## REST API (`b_hydra/api.py`)

`GET /api/info | /api/nodes | /api/chain | /api/block/<i> | /api/tx/<txid>`
`| /api/proof/<txid> | /api/address/<a> | /api/addresses?limit=N (rich list)`
`| /api/balance/<a> | /api/utxos/<a> | /api/mempool`
`POST /api/mine {miner} | /api/transaction {подписанная tx} | /api/send`
`{private_key,to,amount,fee} | /api/wallet {private_key}→адрес+баланс`.

Смарт-контракты: `GET /api/contract | /api/contract/escrow/<id>`
`| /api/contract/cheque/<id>`; `POST /api/contract/escrow (open) |`
`/api/contract/escrow/confirm | /api/contract/escrow/cancel |`
`/api/contract/cheque (write, возвращает секрет ОДИН раз) |`
`/api/contract/cheque/cash {cheque_id,secret,to} | /api/contract/cheque/refund`.

⚠️ `/api/send`, `/api/wallet` и контрактные POST принимают приватный ключ —
это для СВОЕГО локального узла. Для чужого узла нужна подпись на устройстве.
Теперь это ПРАВИЛО В КОДЕ (`_keys_allowed`), а не только в документации: по
TLS — можно, без TLS — только с локального адреса, иначе 403. Перекрывается
явным `--allow-insecure-keys` (для своего обратного прокси с TLS).

## Ключевые факты и подводные камни

- **Адрес**: `"BHY" + base58(0x1f || ripemd160(sha512(pub)) || double_sha512(payload)[:4])`,
  публичный ключ несжатый `0x04||X||Y`. RIPEMD-160 — СВОЙ (`ripemd.py`): в
  сборках OpenSSL 3 его часто нет, а прежний молчаливый откат на
  `sha256(...)[:20]` давал бы РАЗНЫЕ адреса из одного ключа на разных машинах.
  `hashlib` теперь только ускоритель и только после сверки байтов
  (`hashing.ripemd_backend()`).
- **Подпись/txid** считаются от `signing_payload()` =
  `json.dumps({chain_id, vin:[{txid,index}], vout, timestamp}, sort_keys=True, ensure_ascii=False)`.
  `z = int(sha512(payload)[:32])`, подпись `r||s` (low-s). Нонс `k`
  ДЕТЕРМИНИРОВАННЫЙ (RFC 6979, HMAC-SHA512 на нашем хеше) — подпись
  воспроизводима и не зависит от качества ГСЧ.
  ⚠️ **Формат чувствителен к языку**: Python пишет целые суммы как `10.0`, а JS
  «в лоб» — как `10`. Поэтому `bhydra-sign.js` повторяет правила `repr()` из
  CPython (`pythonFloatRepr`), а `tests/test_browser_signing.py` сверяет
  результат с настоящим Python байт-в-байт.
- **Консенсус**: PoW (SHA-512, хеш ≤ target), выбор цепочки по `total_work`
  (не длине), halving каждые 310 000 блоков ПО ВЫСОТЕ (50 → 25 → …; при
  целевом времени блока это ≈29 лет — `economics.halving_years()`, но это
  СЛЕДСТВИЕ, а не правило: по календарю награда зависела бы от часов на
  машине. В белой книге стояло «каждые 4 года» — цифра Bitcoin. Готовый
  раздел для книги, сверенный с кодом тестом, — `ECONOMICS.md`),
  `MAX_SUPPLY=31_000_000`, `chain_id` — защита от replay. Это **линейная
  цепочка**, не DAG.
- **Сложность — LWMA, пересчёт на КАЖДОМ блоке** по скользящему окну
  `RETARGET_INTERVAL=60` (свежие интервалы весят больше). Прежняя схема
  Bitcoin (раз в 100 блоков) при времени блока ~49 мин давала ~3,5 суток
  инерции. Ограничители: вклад блока ≤ `MAX_SOLVETIME_FACTOR=6`×цели,
  шаг ≤ `MAX_ADJUST_FACTOR=4`× за блок, не легче генезиса, не нулевая.
  ⚠️ Ограничитель шага СНИМАТЬ НЕЛЬЗЯ: блоки с одинаковыми метками времени
  (все интервалы = 0) роняют цель до 1, и цепочка становится недобываемой
  навсегда — новых блоков нет, а значит нечему вернуть сложность обратно.
  Сложность следует за РАБОТОЙ, а не за числом участников: `participants()`
  считает адреса, а адрес ничего не стоит (новый адрес на каждый блок раздул
  бы счётчик даром, общий адрес у картеля — занизил).
  ⚠️ Правило консенсуса изменилось: цепочки длиннее окна, добытые по старой
  схеме, невалидны. Короче окна — совпадают побитово (там держится генезис).
- **Метки времени**: три правила, все в `is_chain_valid` (для КАЖДОГО блока,
  не только вершины) и в `node.receive_block` — не раньше предыдущего, строго
  больше медианы последних `MEDIAN_TIME_BLOCKS=11` блоков
  (`median_time_past`, как MTP в Bitcoin) и не дальше `MAX_FUTURE_DRIFT=2` ч
  в будущее. Монотонности одной мало: она разрешала ЗАМОРОЗКУ времени, а при
  LWMA застывшие метки — это нулевые интервалы и разгон сложности. Медиана
  устойчива к выбросу: одиночная метка «из будущего» её не двигает, нужно
  большинство окна.
- **Хеширование**: по умолчанию везде работает SHA-256/512 «с нуля»
  (`sha2.py`, `BHYDRA_PURE_SHA=1`) — байт-в-байт совпадает с `hashlib`, но
  заметно медленнее. Быстрый движок: `BHYDRA_PURE_SHA=0` или
  `hashing.use_pure_sha(False)`.
- **Комиссия решает, что попадёт в блок** — по ставке НА БАЙТ (место в блоке
  ограничено байтами). `mine_pending` собирает блок через `node._by_fee_rate`,
  мемпул при переполнении ВЫТЕСНЯЕТ самое дешёвое (`TransactionPool.add(tx,
  fee=…)`, `cheapest`). Раньше комиссия не влияла ни на что: транзакции брались
  в порядке поступления, а полный мемпул отвечал отказом всем — заплатить за
  срочность было невозможно, и сеть вставала, как только кто-то набивал пул
  копеечными транзакциями.
  ⚠️ Одной сортировкой обойтись НЕЛЬЗЯ: в мемпуле лежат СВЯЗАННЫЕ цепочки
  (потомок тратит неподтверждённую сдачу предка). Окажись потомок раньше
  предка — он не найдёт входа в наборе UTXO и будет отброшен НАВСЕГДА, то есть
  сортировка молча съедала бы переводы. Поэтому `_by_fee_rate` перед каждой
  транзакцией выкладывает её предков (package selection как в Bitcoin, без
  пересчёта ставки пакета).
  ⚠️ Вытеснение требует СТРОГО дороже: при «не дешевле» полный пул можно было
  бы бесконечно перемешивать задаром.
- **`txid` кешируется ПО СОДЕРЖИМОМУ** (`Transaction.txid`): payload собирается
  заново (~6 мкс) и сверяется с тем, от которого считался хеш. Запоминать
  навсегда нельзя — транзакцию достраивают после создания. SHA-512 здесь в
  122 РАЗА дороже сборки payload, а `txid` дёргают постоянно (дедуп, индекс,
  сериализация, поиск в блоке): один `add()` в мемпул трогал его трижды.
  Замер: 10 000 транзакций в мемпул 26,9 → 6,9 с, весь прогон тестов
  236 → 184 с. Остаток — по одному настоящему хешу на транзакцию, он
  неустраним (с hashlib те же 10 000 идут 0,21 с).
  ⚠️ `TransactionPool.remove` выкидывает по ТОЖДЕСТВУ, а не сравнением txid:
  проход по полному пулу с пересборкой payload стоил 6 мс, и при вытеснении на
  каждой вставке это давало секунды (13,8 → 2,2 с).
- **Мемпул** вмещает 10 000+ **связанных** транзакций (кэш «эффективного» UTXO —
  подтверждённые + мемпул — позволяет тратить неподтверждённую сдачу),
  `max_size=50000`; `mine_pending` берёт до `MAX_BLOCK_TRANSACTIONS-1` (4999)
  И не больше `MAX_BLOCK_SIZE` по объёму — узел не должен собирать блок,
  который сам же признает невалидным и не сможет передать. Что не влезло,
  остаётся в мемпуле.
- **Заметка майнера** (`MAX_COINBASE_MESSAGE=100` байт UTF-8) лежит в поле
  `public_key` фиктивного входа coinbase — как scriptSig в Bitcoin, где в
  генезисе «The Times 03/Jan/2009…». Читается через
  `blockchain.coinbase_message(block)` / `node.block_message(index)`, задаётся
  в `mine_pending(addr, message=…)`, CLI `--message`, `POST /api/mine`
  `{message}`; видна в `GET /api/block/<i>` как `miner_message`. Входит в лист
  дерева Меркла, поэтому защищена PoW — переписать задним числом нельзя, не
  перемайнив блок. На txid НЕ влияет (`signing_payload` берёт из входа только
  `txid` и `index`). Лимит — правило сети: блок с более длинной заметкой
  невалиден, иначе в цепочку набивали бы данные, которые все хранят вечно.
- **Подпись заметки** (`mine_pending(addr, message=…, wallet=…)`, CLI `--key`,
  `POST /api/mine {private_key}`): подпись ложится в свободное поле
  `signature` coinbase-входа, публичный ключ — в новое `miner_key`.
  Подписывается `transaction.message_payload` = `{chain_id, height, miner,
  message}` — заметка привязана к сети, ВЫСОТЕ и адресу получателя награды,
  поэтому её нельзя ни переставить в другой блок, ни выдать за свою.
  Проверяет `coinbase_message_author` / `node.block_message_author(index)`
  (в `GET /api/block/<i>` — `miner_message_author`), причём ключ обязан
  соответствовать coinbase-выходу. Подпись НЕОБЯЗАТЕЛЬНА (анонимная заметка
  валидна, как в Bitcoin), но если заявлена — обязана быть настоящей: иначе
  «подпись» была бы просто ещё одним полем свободного текста. Правило сети,
  проверяется в `_validate_block_transactions`. PoW доказывает, что блок
  ДОБЫТ, а не кто написал заметку, — авторство даёт только подпись.
  ⚠️ `miner_key` пишется в dict только у подписанной coinbase: иначе изменился
  бы лист дерева Меркла у всех прежних блоков. Гибридные адреса (`0x2f`)
  заметку пока не подписывают — автор выводится по ECDSA-версии `0x1f`.
- **Размер блока — правило сети**: `MAX_BLOCK_SIZE=4` МиБ проверяется в
  `is_chain_valid` (каждый блок) и в `node.receive_block`. Счётчика
  `MAX_BLOCK_TRANSACTIONS=5000` мало: транзакция с множеством входов/выходов
  может быть сколь угодно большой. Два лимита согласованы — 5000 обычных
  транзакций (~795 байт) это ≈3,79 МиБ, впритык под 4 МиБ.
- **Смарт-контракты** (`ContractManager`) НЕ меняют консенсус: у менеджера свой
  контрактный кошелёк, депозит/выплата/возврат — обычные UTXO-транзакции.
  Конвенция комиссий: плательщик тратит `amount + 2·fee` (депозит + выплата).
  Чек подписан ключом плательщика (`verify_cheque` — офлайн-проверка); секрет
  выдаётся один раз, хранится только его SHA-512. Состояние контрактов API
  сохраняет в `<state>.contracts` (там приватный ключ контракта — не терять).
- **Арифметика кривых — ОДНА на проект** (`ec.py`), кривая передаётся
  параметром `(p, a, b, G, n)`. Раньше её писали ДВАЖДЫ: `wallet.py` считал
  secp256k1, `certgen.py` — свою копию для P-256. Формулы почти одинаковые, и
  ошибка в одной копии не всплыла бы в тестах другой.
  ⚠️ Точки живут в ЯКОБИЕВЫХ координатах: `(X, Y, Z)` = аффинная `(X/Z², Y/Z³)`.
  Смысл в том, что деления в цикле не нужны вовсе — знаменатель копится в Z, и
  инверсия делается ОДИН раз в конце. Замер прежнего аффинного кода: одно
  умножение на скаляр — 385 инверсий, 5,5 мс из 7,0, то есть 79% времени.
  Плюс два приёма: **приём Шамира** в проверке (u1·G + u2·Q одним проходом,
  удвоение общее) и **предвычисленная таблица генератора** (k·G без удвоений
  вовсе). Замер: проверка подписи 12,25 → 1,93 мс (×6,4), вывод ключа из
  приватного 1,48 → 0,07 мс (×20), ECDH рукопожатия 11,94 → 1,49 мс (×8).
  ⚠️ Это НЕ смена правила сети: якобиевы координаты — другая ЗАПИСЬ той же
  группы, результат совпадает до последнего бита. Проверено тремя способами:
  сверкой с независимой аффинной реализацией в `tests/test_ec.py`, прогоном
  150 подписей (верных и порченых) через старый и новый код с нулём расхождений
  и приколоченными подписями `PINNED`, снятыми ДО перехода.
  ⚠️ Таблица генератора ЛЕНИВАЯ: 185 КБ и 12 мс на построение (у 512-битной
  кривой 499 КБ и 62 мс). Окупается с третьего вызова, поэтому одиночная
  подпись в свежем процессе стоит на ~6 мс дороже. Строится одной инверсией на
  все точки сразу (приём Монтгомери: префиксные произведения Z вместо 960
  отдельных инверсий — 24 → 12 мс).
  ⚠️ Подпись ускорилась только в 2,2 раза (10,40 → 4,76 мс), потому что теперь
  в ней 78% — вывод нонса RFC 6979 на нашем чистом SHA-512, а сама кривая 5%.
  Дальше ускорять надо ХЕШ, а не кривую — то есть ровно наоборот к тому, что
  было верно до этой правки.
  ⚠️ Кривой **`secp512k1` НЕ СУЩЕСТВУЕТ**: семейство SEC «k» (Коблица) кончается
  на secp256k1, дальше только «r» — secp384r1 и secp521r1 (521 бит, а не 512:
  там простое Мерсенна 2⁵²¹−1). Настоящая стандартная кривая на 512 бит —
  `brainpoolP512r1` (RFC 5639), она и лежит в таблице ДЛЯ ОПЫТОВ. В консенсус
  она не идёт и не должна: secp256k1 даёт 128 бит стойкости (2¹²⁸ операций
  Полларда), а от кванта размер кривой не спасает вообще — Шор ломает любую
  кривую независимо от длины поля, и ответ кванту в проекте другой, правильный
  (гибридные адреса `0x2f` с XMSS). Цена замерена: умножение на скаляр 1,9 мс
  против 11,0 мс, проверка подписи 4 мс против 22 мс. Своя кривая была бы худшим
  выбором: подбор параметров требует счёта числа точек (SEA), доказательства
  простоты порядка и проверки MOV-вложения — взять p и b наугад значит, возможно,
  получить сломанную кривую и не узнать об этом.
  ⚠️ Параметры всех трёх кривых сверяются с ЧУЖИМ эталоном: openssl генерирует
  ключ, и наш `k·G` обязан дать тот же публичный ключ
  (`test_openssl_agrees_about_the_public_key`). Сверка с самим собой поймала бы
  опечатку в формуле, но не в константе.
- **Скорость подписи**. Замер приёма транзакции: 15,5 мс, из них 12,2 —
  проверка подписи, а хеш всего 5%. Поэтому ускорять надо КРИВУЮ, а не SHA.
  ⚠️ Этот вывод ПЕРЕСТАЛ БЫТЬ ВЕРНЫМ после перехода на `ec.py`: чистый Python
  проверяет подпись за 1,93 мс, и в подписи теперь 78% — нонс RFC 6979 на нашем
  SHA. Нативный бэкенд по-прежнему нужен (0,71 мс против 1,93), но выигрыш стал
  ×2,8 вместо ×17 — потому что подтянулся эталон, а не просел C++.
  Порядок бэкендов `Wallet.verify` (активный — `wallet._BACKEND`):
  1. **свой C++** `cpp/bhydra_ec_lib.cpp` через ctypes (`native_ec.py`) — то же
     уравнение из `bhydra_ec.hpp`, что и в рукопожатии транспорта, чужой
     крипты не добавляется. Замер: проверка 12,24 → 0,71 мс (×17), приём
     транзакции 15,49 → 3,66 мс (×4,2);
  2. сторонний `coincurve` (libsecp256k1) — быстрее, но библиотека чужая,
     поэтому только если своей нет;
  3. чистый Python.
  ⚠️ Библиотека, а не команда (как у майнера): там срез в секунду покрывает
  запуск процесса, здесь работы на полмиллисекунды — процесс стоил бы дороже
  проверки. У ctypes обязательны `argtypes`.
  ⚠️ Множество принимаемых подписей обязано СОВПАДАТЬ с чистым Python: разойдись
  оно, узлы с библиотекой и без неё по-разному решали бы, какая транзакция
  валидна — раскол сети. Поэтому `_selftest_backend` гоняет живые подписи и
  проверяет ОБЕ половины (верную принять, подделку отвергнуть): ядро «да на
  всё» — самая опасная поломка, и односторонняя проверка его бы пропустила.
- **Сетевые лимиты** (`p2p.py`): таблица пиров `MAX_PEERS=256`, не больше
  `MAX_PEERS_PER_MESSAGE=32` адресов в одном сообщении (и принимаем, и
  отдаём — чтобы порча не расползалась), обход пиров ПАРАЛЛЕЛЬНЫЙ
  (`_fanout`, `FANOUT_WORKERS=32`), `peer_timeout=2` с, `inbound_timeout=10` с,
  `MAX_INBOUND_CONNECTIONS=64` и не больше `MAX_INBOUND_PER_HOST=16` с одного
  хоста. Без этого один пир парализовал узел: список несуществующих адресов +
  последовательный обход с таймаутом = десятки минут на один блок. Таблица
  пиров закрыта `_peers_lock`, обход идёт по снимку `peer_list()`.
  ⚠️ Лимит на хост появился ВМЕСТЕ с постоянными соединениями: пока сокет жил
  одно сообщение, слот освобождался сам через миллисекунды, а постоянный
  держится, пока пир его не отпустит, — один сосед занял бы все 64 слота
  совершенно легально, просто изредка пингуя. Loopback не ограничен (как и не
  банится): демо и тесты поднимают десятки узлов на 127.0.0.1.
- **Узел обслуживает себя САМ** (`P2PNode.start_maintenance`,
  `MAINTENANCE_INTERVAL=15` с): раз в интервал `discover_peers()` + `sync()`.
  Анонсы приносят только то, что произошло ПРИ НАС — сосед рассылает `inv` в
  момент, когда добыл блок, и старые блоки никто не перешлёт по своей воле.
  Узел, постоявший выключенным или потерявший связь, без этого остался бы на
  своей высоте навсегда. Раньше цикл жил в `api.py`, поэтому узел из `P2P.py`
  обслуживал себя только реактивно — поведение зависело от способа запуска.
  ⚠️ По умолчанию ВЫКЛЮЧЕНО, включают точки входа: в тестах десятки узлов, и
  фоновые сетевые вызовы у каждого сделали бы сюиту плавающей.
  ⚠️ `stop()` будит цикл сразу (через `Event`, а не `sleep`) — иначе
  «остановленный» узел ещё до 15 с ходил бы по сети.
  ⚠️ Молчащий сосед из таблицы НЕ выкидывается: `_fanout` пропускает
  недоступных, убираются только ответившие из ЧУЖОЙ сети. Перезагрузка соседа
  не должна стоить записи о нём.
  ⚠️ Вернуться должен ТОТ ЖЕ узел: закрепление ключа (TOFU) считает свежий ключ
  на знакомом адресе подменой, а не возвращением, и чужую цепочку не примет.
  Иначе достаточно было бы дождаться отключения соседа и занять его адрес.
- **`sync()` выбирает пира по работе**, а не по высоте — то же правило, что и
  `replace_chain`. `get_height` отвечает `{height, work}`; поле `work`
  необязательное (пиры старых версий сравниваются по высоте).
- **Опознание сети при handshake**: `hello` несёт `{chain_id, genesis}`
  (`network_id()`/`same_network()`), и пир с чужим генезисом в таблицу не
  попадает — ни через `hello`, ни через список пиров, ни через UDP-маяк.
  Отсутствие полей = несовпадение (иначе проверку обходили бы, не присылая их).
  Это ОПОЗНАНИЕ сети, а не аутентификация: узлы с разной базовой сложностью
  имеют разный генезис, и их цепочки несовместимы. ⚠️ Протокол несовместим со
  старыми узлами: те не присылают отпечаток и будут отвергнуты.
- **Репутация пиров**: за нарушения начисляются штрафные очки, при
  `BAN_SCORE=100` адрес банится на `BAN_DURATION=3600` с и выкидывается из
  таблицы (`is_banned`/`ban_peer`/`ban_score`). Штрафы: битое сообщение 25,
  негодный блок 50, чужая сеть 20, мусор в списке адресов 10. Бан по ХОСТУ —
  у входящего соединения виден только IP, порт там эфемерный. Забаненному
  отказывают сразу в `accept()`, до разбора сообщения. Одиночная оплошность
  прощается через `SCORE_RESET_AFTER=600` с — наказываем всплеск, а не сбой.
  ⚠️ Блок «из будущего» (мы отстали) НЕ штрафуется: честный майнер впереди не
  виноват. ⚠️ Loopback по умолчанию не банится (`ban_loopback=False`): в
  реальной сети таких пиров нет, а демо и тесты живут на 127.0.0.1, где один
  банлист положил бы все узлы машины.
- **Узел переживает перезапуск**: таблица пиров сохраняется на диск
  (`peers_file`, атомарная запись, `stop()` тоже сохраняет), а для первого
  запуска есть `seeds` (`--seed`, `BHYDRA_SEEDS=host:port,...`) и
  `bootstrap()`. Без этого узел в интернете после рестарта оставался ОДИН:
  UDP-маяк работает только в пределах локальной сети.
  ⚠️ `sync()` пробует НЕСКОЛЬКО кандидатов (`SYNC_PEER_ATTEMPTS=4`), а не
  только лучшего: пир, объявивший огромную работу, всегда выигрывает выбор — и
  пока пробовался один, упавший или лгущий сосед намертво перекрывал
  синхронизацию с честными.
  ⚠️ `stop()` делает `shutdown()` перед `close()`: одного `close()` мало —
  поток, висящий в `accept()`, не просыпается, и «остановленный» узел
  продолжает отвечать.
- **Блок рассылается АНОНСОМ** (`inv` с хешем), тело сосед забирает сам через
  `get_block`. Раньше полный блок улетал каждому пиру, даже тому, у кого он уже
  есть: трафик = размер блока × число соседей. Замер на блоке в 61 транзакцию и
  8 соседях: 1,6 КБ анонсов против 390 КБ тел — в 241 раз меньше.
  ⚠️ Распространение стало АСИНХРОННЫМ: `mine()` возвращает управление после
  анонса, тело соседи качают сами — в тестах нужен `_wait_until`. Тело качается
  только у того, кто реально соединился (хост берётся из соединения, не из
  сообщения), дедуп по хешу, потолок `MAX_INFLIGHT_FETCHES=16`.
- **Транзакция рассылается ТАК ЖЕ анонсом** (`inv` с `kind:"tx"`), тело сосед
  забирает через `get_tx {txid}` → `tx_body`. Прежде тело улетало каждому
  соседу, и в связной сети один и тот же байт приходил столько раз, сколько у
  узла соседей: каждый пересылал его дальше, а получатель отбрасывал по
  дедупу — трафик тратился уже ПОСЛЕ того, как становился ненужным. Замер на
  полносвязной сети из 6 узлов: обычная транзакция (777 Б) 25,0 → 13,8 КБ,
  крупная с 20 входами (8,8 КБ) 226 → 51 КБ (в 4,4 раза меньше; чем больше
  транзакция, тем больше выигрыш). Мемпул умеет `get(txid)` — O(1) по индексу,
  иначе `get_tx` перебирал бы 50 000 транзакций на каждый анонс.
  ⚠️ Распространение транзакций тоже стало АСИНХРОННЫМ: `submit_transaction`
  возвращает управление после анонса — в тестах нужен `_wait_until`. Пир обязан
  прислать именно то, что анонсировал: txid ПЕРЕСЧИТЫВАЕТСЯ от содержимого, а
  не берётся из присланного JSON. Свой потолок докачек
  `MAX_INFLIGHT_TX_FETCHES=32`, отдельный от блочного: поток анонсов транзакций
  не должен вытеснять докачку блоков — блоки двигают консенсус.
- **Канал ШИФРУЕТСЯ** (`secure.py`, по умолчанию `encrypt=True`): эфемерный ECDH
  на secp256k1 (`wallet._scalar_mult`, ключи одноразовые → прямая секретность),
  поток на SHAKE-256 с XOR, целостность HMAC-SHA512 (Encrypt-then-MAC, тег до
  расшифровки), ключи РАЗНЫЕ по направлениям (иначе кадр отражался бы узлу
  обратно), у кадров порядковые номера строго подряд (закрывает и повтор, и
  ВЫБРАСЫВАНИЕ кадра — «не меньше прошлого» разрешало бы тихо потерять анонс).
  Подлинность узла: сервер подписывает стенограмму рукопожатия долговременным
  ключом УЗЛА (`identity`, файл `bhydra_identity.json`, 0600 — это НЕ ключ
  кошелька, его утечка позволяет выдать себя за узел, но не тронуть монеты).
  Клиент закрепляет ключ при первом контакте (TOFU, как в SSH) и требует его
  впоследствии; закрепления живут в файле пиров рядом с адресами.
  Замер прослушкой настоящего соединения: в открытом канале находились адрес
  майнера, адрес получателя, txid, тип сообщения и поле подписи (99% печатных
  символов) — в шифрованном ни одного из них (35%, только рукопожатие видно).
  Цена: рукопожатие ~90 мс (ECDH+подпись+проверка на чистом Python), дальше
  +0,1 мс на сообщение; поток 37–63 МиБ/с (блок в 4 МиБ — 64 мс).
  ⚠️ Шифрование посильно ТОЛЬКО из-за постоянных соединений: рукопожатие
  платится раз на соединение, а не раз на сообщение. Sync 120 блоков:
  28 мс открытым каналом против 105 мс шифрованным — разница и есть одно
  рукопожатие.
  ⚠️ ПОНИЖЕНИЯ ВЕРСИИ НЕТ: сорванное рукопожатие — отказ соединения, а не
  откат на открытый текст. Молчаливый откат — ровно то, чего добивается
  активный атакующий. Открытый узел — только явным `encrypt=False`
  (`--no-encrypt`); сервер при этом терпит открытых клиентов, чтобы такой узел
  не оказался отрезан, а `require_encryption=True` закрывает и это.
  ⚠️ Чего НЕ даёт: активный посредник при ПЕРВОМ контакте с новым пиром
  подменит ключ незаметно (как в SSH); со второго раза видно. Клиент себя не
  аутентифицирует — у входящего всё равно виден только IP, по нему и баны.
  UDP-маяки не шифруются: там только «я узел на порту N» и отпечаток сети.
  ⚠️ У транспорта есть ВТОРАЯ реализация — нативная, `cpp/` (см. там README).
  Тот же протокол байт-в-байт, сверяется в `tests/test_cpp_secure.py`: хеши,
  ECDH, подписи, ключи сессии, кадры + живое рукопожатие через сокет в обе
  стороны и запрос к настоящему `P2PNode`. Замер: рукопожатие 65 → 2,2 мс
  (в 29 раз), подпись 12,4 → 0,32 мс, проверка 14,6 → 0,57 мс. ⚠️ А вот ПОТОК
  шифра в Python БЫСТРЕЕ (42 мс на 4 МиБ против 91): там работает
  `hashlib.shake_256`, то есть оптимизированный C, и простой перенос на C++ его
  не обогнал. Выигрыш нативного кода — там, где Python считает САМ (кривая).
  Меняешь протокол — правь обе реализации, тест поймает расхождение.
  ⚠️ Шифруется канал УЗЕЛ↔УЗЕЛ. У REST свой, НАСТОЯЩИЙ TLS — см. ниже.
  ⚠️ При DecryptError соединение закрывается БЕЗ штрафа: испортить кадр может
  кто-то НА ПУТИ, и наказание позволило бы ему ссорить нас с честными пирами.
  ⚠️ Здесь hashlib (SHAKE-256/HMAC), а не наш чистый SHA, — единственное место
  в проекте. Замер: keystream на нашем Python-SHA 0,18 МиБ/с, то есть блок в
  4 МиБ шифровался бы 22 с. Правило «своё, hashlib только ускоритель» держится
  там, где нужна ВОСПРОИЗВОДИМОСТЬ снаружи (адреса, txid, Меркл); транспортный
  шифр никто не пересчитывает офлайн, он живёт одну сессию. Байты SHAKE-256
  сверяются с вектором NIST при импорте (`secure._selftest`).
- **У REST — НАСТОЯЩИЙ TLS** (`--tls`, `api.make_tls_context`): стандартный
  `ssl` поверх OpenSSL, минимум TLS 1.2. Свой TLS для БРАУЗЕРА писать нельзя —
  собственный протокол `secure.py` уместен между нашими узлами, но не там, где
  на другом конце чужой стек. Чего в stdlib нет — выпуска сертификата, поэтому
  `certgen.py` собирает его сам: ASN.1/DER, ключ ECDSA P-256, подпись SHA-256 с
  нонсом по RFC 6979 (тот же `_rfc6979_nonces`, он для этого и параметризован).
  Так `--tls` работает без openssl в системе и без pip install.
  ⚠️ P-256, а НЕ secp256k1: нашу кривую TLS не принимает, её убрали из
  умолчаний. Отличие только в коэффициенте `a` (здесь `p-3`, в кошельке 0).
  ⚠️ Имя проверяется ТОЛЬКО по subjectAltName — CommonName для этого не

- **RSA с нуля** (`rsa.py`) — ещё один чужой формат, реализованный своими
  руками, как SHA, RIPEMD, QR, PNG и X.509. ⚠️ В КОНСЕНСУС НЕ ВХОДИТ и входить
  не должен: подписи транзакций делает ECDSA на secp256k1, смена схемы подписи
  — смена правила сети. RSA нужен там, где на другом конце ЧУЖОЙ инструмент
  (подпись APK, сертификаты, обмен ключами со старым софтом).
  ⚠️ «RSA из учебника» (`pow(m,e,n)`) СЛОМАН, и это не придирка: шифр
  детерминированный (короткая сумма перевода подбирается перебором), малое
  сообщение при e=3 достаётся обычным кубическим корнем, шифр малеабелен
  (`c·sᵉ` превращает m в m·s — подпись «переводу на 1» становится подписью
  переводу на 1000), а подпись без набивки подделывается перемножением двух
  чужих. Поэтому здесь **OAEP** для шифрования и **PSS** для подписи (RFC 8017),
  а PKCS#1 v1.5 — только потому, что без него не разговаривает почти весь
  существующий софт (тот же `jarsigner`).
  ⚠️ Приватная операция — CRT + ОСЛЕПЛЕНИЕ + проверка результата публичным
  ключом. Ослепление обязательно: без него время работы зависит от секретного
  показателя. Проверка обязательна тоже — единственная аппаратная ошибка при
  CRT-подписи РАСКРЫВАЕТ ключ (по НОД разности с модулем), поэтому подпись
  сверяется до того, как уйдёт наружу. Замер (2048 бит, чистый Python-SHA):
  генерация 0,76 с, OAEP 2,1/10,3 мс, PSS 9,9/1,7 мс — и это БЫСТРЕЕ голого
  `pow(c, d, n)` (24,2 мс), несмотря на ослепление и проверку.
  ⚠️ `d` считается по функции Кармайкла λ(n), а не по Эйлеру φ(n) (так требует
  нынешняя редакция стандарта), а слишком маленький `d` отвергается — иначе
  ключ достаётся атакой Винера, не трогая модуль. `|p − q|` проверяется:
  близкие простые факторизуются методом Ферма за секунды.
  ⚠️ Все неудачи OAEP дают ОДНУ ошибку без подробностей: по тому, как именно
  отвергнут шифротекст, его читают целиком (атака Мангера). По той же причине
  разделитель ищется БЕЗ раннего выхода, а сравнение — константное по времени.
  ⚠️ Сюда же входят отказы ПРИВАТНОЙ ОПЕРАЦИИ: она говорит «шифротекст вне
  диапазона модуля» и «сбой приватной операции», и наружу эти слова уходить не
  должны. Это не теория — утечка была: при c ≥ n отказ отличался от всех
  остальных, а границу модуля атакующий нащупывает первой, и по ней
  восстанавливается старший байт открытого текста. Поймал
  `test_oaep_failures_look_identical`, но НЕ сразу: он попадал в эту ветку по
  удаче (порча старшего байта делает c ≥ n не на каждом ключе), и падение
  выглядело плавающим. Теперь c ≥ n подаётся явно.
  ⚠️ Чем проверено: не «сошлось с самим собой», а ЧУЖИМ инструментом — в обе
  стороны. `tests/test_rsa.py` гоняет `openssl`: наш ключ читает openssl, наши
  PSS и v1.5 он проверяет, его ключ (PKCS#8) читаем мы, его подписи проверяем,
  его OAEP расшифровываем и он расшифровывает наш.
  ⚠️ OpenSSL 3 пишет приватный ключ в **PKCS#8**, а публичный — в **SPKI**, а не
  в голый PKCS#1, поэтому `_unwrap` распознаёт обе обёртки. Первая попытка
  читать вывод openssl падала именно на этом.
  ⚠️ Чего НЕ даёт: арифметика больших чисел в Python не постоянная по времени, и
  сделать её такой нельзя. Ослепление закрывает утечку через показатель, но от
  атакующего НА ТОЙ ЖЕ машине набивка не спасёт — для смарт-карты это негодно.

- **APK собирается БЕЗ Android SDK** (`apkbuild.py`): APK — это ZIP из четырёх
  частей, и каждая делается доступным средством. Двоичный `AndroidManifest.xml`
  (AXML) — свой кодировщик `axml.py`; `classes.dex` — официальный `dx` с Maven
  Central; подпись — `jarsigner` из JDK; архив — `zipfile`. SDK нужен был ровно
  ради AXML, поэтому он и написан.
  ⚠️ Атрибуты `android:*` опознаются НЕ по имени, а по 32-битному ресурсному id
  из карты ресурсов. Неверный id — атрибут молча игнорируется (например,
  приложение остаётся без интернета). Поэтому неизвестный атрибут — ОШИБКА
  сборки, а результат читается обратно ЧУЖИМ разборщиком (`pyaxmlparser`), а не
  нашим же кодом.
  ⚠️ И сами id сверяются с ЧУЖОЙ таблицей — `public.xml` платформы (внутри
  `pyaxmlparser`), тест `test_attribute_ids_match_the_platform_table`. Это не
  теория: у `usesCleartextTraffic` стоял `0x0101076E` вместо `0x010104EC`, и
  APK, прошедший ВСЕ прежние проверки, на живом телефоне падал на первой же
  странице с `ERR_CLEARTEXT_NOT_PERMITTED` (для `targetSdk ≥ 28` открытый HTTP
  запрещён по умолчанию, а разрешение до системы не доходило). Прежний тест
  сверял карту ресурсов с `ATTRIBUTE_IDS`, то есть таблицу саму с собой, а
  `pyaxmlparser` читает имя атрибута из строкового пула и на неверный id не
  жалуется. Атрибута, которого нет в эталоне, в таблице быть не должно
  (`compileSdkVersion`, `appComponentFactory` убраны): лучше ошибка сборки,
  чем тихо потерянная настройка.
  ⚠️ Карта ресурсов параллельна НАЧАЛУ строкового пула: имена атрибутов обязаны
  идти первыми и в том же порядке, иначе каждый получит чужой id.
  ⚠️ `targetSdk=29` намеренно: с 30 Android требует подпись v2, а её делает
  `apksigner` из SDK. Ресурсов (`resources.arsc`) нет — их собирает `aapt2`,
  поэтому ссылки `@mipmap/...` из манифеста выбрасываются (иконка системная).
  ⚠️ В `MainActivity.java` не должно быть ни androidx (он на Google Maven), ни
  своих `R.*`, ни лямбд (`dx` не понимает invokedynamic из Java 8) — это
  закреплено тестом.
  ⚠️ APK здесь запустить НЕЛЬЗЯ: нет ни устройства, ни эмулятора (на телефоне
  его проверяет владелец — так и нашёлся баг с `usesCleartextTraffic`).
  Проверено другое — структура архива, разбор чужим парсером, контрольные суммы
  DEX (Adler-32 и SHA-1), `jarsigner -verify` и СОДЕРЖИМОЕ байт-кода:
  `apkbuild.dex_references` читает таблицы строк/типов/методов DEX напрямую и
  сверяет `REQUIRED_CALLS` с тем, что реально попало в `classes.dex`.
  «Собралось» ничего не доказывает: пропади из исходника
  `setDomStorageEnabled`, javac и `dx` промолчат, APK установится — и кошелёк
  будет терять приватный ключ при каждом закрытии (он живёт в `localStorage`).
  Оттуда же видно, что в байт-коде нет ни `Landroidx/`, ни `Ljava/lang/invoke/`.
  ⚠️ `jarsigner -verify` печатает «Invalid certificate chain» — так и должно
  быть: подпись самоподписанная, центра у неё нет. Android проверяет не доверие,
  а неизменность подписи между обновлениями.
- **Майнер умеет БРОСАТЬ блок** (`Block.mine_block(should_stop=…)`). Прежний
  цикл `while int(self.hash,16) > target` выйти было НЕЧЕМ: сосед прислал
  блок — наш родитель устарел, а узел продолжал молотить и потом сам же свой
  блок отклонял. Теперь `p2p.mine` сдаётся, как только сменилась вершина
  (`node.mine_pending(should_stop=…)` → None), и REST отвечает 409.
  ⚠️ Транзакции ВОЗВРАЩАЮТСЯ в мемпул (`node._return_to_mempool`): их снимают
  ДО майнинга, и без возврата брошенный блок молча съедал бы чужие переводы.
  Возврат ДОКЛАДЫВАЕТ, а не заменяет список — пока шёл перебор, могли прийти
  новые транзакции.
  ⚠️ `max_attempts` проверяется КАЖДУЮ попытку (иначе `max_attempts=1` молча
  превращался в 512), а `should_stop`/`on_progress` — раз в
  `MINING_CHECK_INTERVAL=512`: на быстром движке это миллионы вызовов в
  секунду, опрос стоил бы дороже перебора. Цена точного бюджета — 1–2%.
- **Скорость майнинга ×3** двумя приёмами, НЕ меняющими хеш: midstate
  (`hashing.sha512_hasher` — неизменная часть заголовка сжимается один раз,
  дальше копируется состояние; `copy()` есть и у `hashlib`, и у нашего
  `sha2.Sha512`, поэтому ускоряются ОБА движка) и сравнение 64 БАЙТ вместо
  `int(hash,16)` на каждой попытке (замер: перевод hex в число — 17% стоимости
  хеша, сравнение байтов — 3%). Замер: чистый Python 992 → 3 051 хеш/с,
  hashlib 306 639 → 956 816 хеш/с.
  ⚠️ Формат заголовка (`header_prefix` + `nonce`) менять НЕЛЬЗЯ — изменится
  хеш, и вся существующая цепочка станет невалидной. Закреплено

- **Нативный майнер** (`cpp/bhydra_miner.cpp`, `native_miner.py`): тот же

  НЕ быстрее — `hashlib` это OpenSSL, и наш SHA-512 с ним вровень. Весь

  ⚠️ Результату майнера НЕ ВЕРЯТ: `Block._mine_native` пересчитывает хеш своим

- **Майнинг на ВИДЕОКАРТЕ** (`gpu/bhydra_miner.cl` + `gpu_miner.py`,
  `python -m b_hydra.gpu_miner`, `BHYDRA_GPU`). Перебор nonce — единственная
  задача проекта, которая ложится на GPU: тысячи НЕЗАВИСИМЫХ попыток, общей
  памяти нужно на одно слово (флаг «нашли»). Подпись, проверка цепочки и сеть
  туда не поедут — там короткие зависимые цепочки, GPU там медленнее CPU.
  Порядок движков в `mine_block`: видеокарта → все ядра CPU → чистый Python.
  ⚠️ **Собирать нечего**: ядро компилирует драйвер при запуске. `libOpenCL`
  грузится через `ctypes` — без `pyopencl`, правило «ноль обязательных
  зависимостей» держится. OpenCL, а не CUDA: одинаково работает на NVIDIA, AMD
  и Intel и не требует `nvcc`.
  ⚠️ Интерфейс НАМЕРЕННО тот же, что у `native_miner.py`
  (`selftest`/`mine`/`benchmark`), поэтому `mine_block(miner=…)` принимает GPU
  без единой правки — и вместе с ним даром достаются срезы по времени (право
  бросить блок) и проверка результата в `_mine_native`.
  ⚠️ nonce приписывается ДЕСЯТИЧНОЙ строкой, как `str(nonce)` в Python. Возьми
  ядро двоичный nonce — хеши сходились бы сами с собой, но не с сетью, и каждый
  добытый блок отвергался бы всеми.
  ⚠️ Ядро отдаёт наружу и САМ ДАЙДЖЕСТ, а не только nonce: иначе Python сравнил
  бы свой хеш сам с собой, и ядро с ЧУЖИМ SHA-512 прошло бы проверку незаметно.
  ⚠️ Расписание раундов живёт в ОКНЕ ИЗ 16 СЛОВ, а не в массиве на 80 (формула
  дальше 16 назад не смотрит): 128 байт приватной памяти на work-item вместо
  640. На GPU приватная память — это регистры, и при нехватке компилятор
  выселяет расписание в глобальную. Замер на CPU-устройстве, где эффект слабее
  всего: при 65536 work-item 4,13 → 6,62 Мхеш/с, и провал на больших запусках
  исчез совсем.
  ⚠️ САМО СОБОЙ берётся только настоящая видеокарта: CPU-устройства OpenCL
  (POCL, драйверы Intel) считают те же хеши на тех же ядрах, только через
  драйвер, и молча подменять ими нативный майнер незачем. Явным `BHYDRA_GPU`
  берётся любое — на этом и держатся тесты.
  ⚠️ Устройство обязано быть little-endian (слова кладутся в буферы в порядке
  хоста) — проверяется явно. Отвалившийся драйвер не теряет блок: перебор молча
  продолжается на процессоре.
  ⚠️ `NONCE_CEILING`: в ядре nonce 64-битный, а в Python сколь угодно большой,
  и `ctypes.c_ulonglong(2**64)` молча даёт 0 — не отказ, а тихая подмена.
  Заворот сделан явно.
  ⚠️ **ЖИВОГО GPU НЕ ВИДЕЛ НИКТО**: видеокарты в контейнере нет. Проверена
  ПРАВИЛЬНОСТЬ — ядро выполняется на CPU-устройстве OpenCL (POCL), дайджест
  сверяется с нашим SHA-512 побайтово на границах блока (127/128/129 байт) и на
  разном числе цифр nonce, пространство поиска сужается до ОДНОГО nonce (иначе
  подошёл бы любой удачный, и проверка была бы «нашлось хоть что-то»),
  проверяется и обратная половина (не подошёл — не найден), добывается цепочка
  и проходит `is_chain_valid()`, врущий майнер ловится. НЕ проверены скорость на
  живом железе, драйверы NVIDIA/AMD/Intel и подбор `work_size`/`per_item` под
  конкретную карту.
- **IPv6 наравне с IPv4** (`transport.py`: `listen`/`connect`, разбор адресов).
  У домашних провайдеров IPv4 всё чаще за CGNAT — входящее соединение туда не
  доходит, и узел виден только исходящими; IPv6 при этом выдаётся честный и
  часто оказывается ЕДИНСТВЕННЫМ способом принять соседа.
  ⚠️ Слушаем ОДНИМ сокетом: `AF_INET6` с выключенным `IPV6_V6ONLY` принимает обе
  семьи. Два сокета потребовали бы второго потока `accept()` и удвоили бы весь
  учёт соединений. Откат на чистый IPv4 обязателен: `IPV6_V6ONLY` выключается
  не везде (OpenBSD запрещает), а `AF_INET6` может отсутствовать вовсе.
  ⚠️ Исходящие идут через `socket.create_connection`, а не `AF_INET` вручную:
  он перебирает все адреса из `getaddrinfo`. Прежде узел с одной AAAA-записью
  в DNS был недостижим, а имя с двумя записями всегда шло по IPv4.
  ⚠️ `::ffff:1.2.3.4` — ЭТО ТОТ ЖЕ адрес, что `1.2.3.4`, только записанный
  по-другому, и двойной стек отдаёт IPv4-соседей именно так. Без сведе́ния
  (`normalise_host`) один сосед занимал бы две записи в таблице, вдвое обходил
  бы лимит соединений с хоста, а бан одной формы не действовал бы на вторую.
  Сведение применяется в `add_peer`, `is_banned`, `ban_peer`, `_penalise`,
  `_is_loopback` и в `accept` транспорта.
  ⚠️ Сведение — через `ipaddress`, а НЕ обрезкой строки. У одного и того же
  /128 написаний десятки: ведущие нули независимо в каждой из восьми групп,
  `::` на любом месте нулевой серии, регистр hex. Пока написания сравнивались
  строками, сосед переписыванием собственного адреса заводил себе новый
  счётчик `MAX_INBOUND_PER_HOST` на каждую форму, раздувал таблицу пиров и
  уходил от бана. `ipv4_mapped` заодно ловит `0:0:0:0:0:ffff:1.2.3.4`, который
  проверка по префиксу `::ffff:` пропускала.
  ⚠️ Формат адреса: IPv6 пишется В СКОБКАХ (`[2001:db8::1]:5000`, RFC 3986) —
  это единственная однозначная запись, и именно её напечатает человек. Прежний
  разбор `rpartition(":")` давал на ней хост `[2001:db8::1]`, с которым
  соединиться нельзя. **Ключи IPv4 не изменились ни на байт** (`join_host_port`
  ставит скобки только при двоеточии в хосте), поэтому файл пиров и сообщение
  `peers` читаются узлами прежних версий как раньше.
  ⚠️ ГОЛЫЙ IPv6 парой «хост и порт» НЕ СЧИТАЕТСЯ: отличить `2001:db8::1:5000`
  от «`2001:db8::1` на порту 5000» нельзя в принципе, обе записи законны.
  `rpartition(":")` резал такую строку по последнему двоеточию и превращал
  `2001:db8::1` в хост `2001:db8:` с портом 1 — узел ходил стучаться в
  несуществующий адрес. Строки приходят и из `peers`-сообщения соседа, то есть
  таблицу можно было засорять УДАЛЁННО. Терять нечего: пишет адреса только
  `join_host_port`, а он IPv6 всегда берёт в скобки.
  ⚠️ В скобках обязан быть настоящий IPv6-литерал, порт — лежать в 1..65535:
  `[not-an-addr]:80` и `1.2.3.4:0` соединением не станут никогда.
  ⚠️ `_DualStackServer.address_family` берётся через `getattr`: тело класса
  выполняется НА ИМПОРТЕ, а на сборке Python без IPv6 атрибута `AF_INET6` нет —
  прямая ссылка роняла бы импорт всего `api.py`, и вместо отката на IPv4 узел
  просто не стартовал бы. По той же причине в `server_bind` к `OSError`
  добавлен `AttributeError`.
  ⚠️ У REST свой сервер: `ThreadingHTTPServer` умеет только IPv4, поэтому
  добавлен `_DualStackServer` — иначе кошелёк в сети без IPv4 до узла не
  достучался бы.
  ⚠️ UDP-МАЯК ОСТАЛСЯ IPv4: широковещания в IPv6 нет вовсе, там нужна
  многоадресная рассылка на `ff02::1` — это отдельный механизм, и проверить его
  здесь нечем. Автопоиск в локальной сети работает по IPv4, соединения — по обеим.
  ⚠️ **ЖИВОГО IPv6 НЕ ВИДЕЛ НИКТО**: в контейнере разработки его нет совсем
  (`AF_INET6` → «Address family not supported by protocol», интерфейсов ноль).
  Проверены разбор и запись адресов, сведение написаний, таблица пиров и баны,
  переживание перезапуска и ОТКАТ на IPv4 (эта ветка тут как раз рабочая).
  НЕ проверено живое соединение по IPv6 и приём IPv4 через двойной стек —
  эти два теста включатся сами там, где IPv6 есть.
- **Транспорт подменяем** (`transport.py`): протокол выше сокета про TCP не
  знает — `tcp.py` пользуется только `sendall`/`recv`, `secure.py` ими же плюс
  таймаутами. Поэтому сеть переносится на любой БАЙТОВЫЙ ПОТОК подменой одного
  объекта: `P2PNode(..., transport=...)`. Интерфейс из четырёх методов:
  `listen`/`accept`/`connect`/`close_listener`. Адрес везде пара «хост + номер»
  (TCP: IP и порт; Bluetooth RFCOMM: MAC и канал), поэтому `send(host, port)`
  не менялся. Сделано под D2D — Bluetooth-сокеты уже есть в stdlib
  (`AF_BLUETOOTH`/`BTPROTO_RFCOMM`, Linux), а на Android их API только в Java,
  так что C++ там ничего не даёт.
  ⚠️ `close_listener` — отдельный метод, а не `server.close()`: у TCP закрытия
  мало, поток в `accept()` от него не просыпается (та же причина, что у
  `stop()`). Как будить — знает только транспорт.
  ⚠️ Маяки (UDP-широковещание) в интерфейс НЕ входят: широковещания нет ни у
  Bluetooth, ни у «точки-точки». Флаг `supports_discovery`, и `start_discovery()`
  честно возвращает False вместо потоков, которые ничего не найдут.
  ⚠️ Что абстракция настоящая, доказывает `PairTransport` (`socket.socketpair()`,
  AF_UNIX): в `tests/test_transport.py` поверх него идут рукопожатие, шифрование,
  анонсы, майнинг и синхронизация — БЕЗ IP вообще. Замер: накладных расходов
  нет (ping 0,19 → 0,17 мс).
- **Bluetooth-транспорт = D2D без роутера** (`BluetoothTransport`,
  `cpp/bhydra_bt.cpp`, `--transport bluetooth`). Разделение языков ЖЁСТКОЕ и не
  случайное: соединение по RFCOMM — Python (в stdlib есть `AF_BLUETOOTH`/
  `BTPROTO_RFCOMM`, а RFCOMM это байтовый поток, поэтому кадры и шифрование
  идут поверх без правок), а ПОИСК устройств вокруг — C++, потому что
  `hci_inquiry` из BlueZ в Python нет вовсе. Здесь C++ нужен НЕ ради скорости
  (в отличие от `bhydra_secure.hpp` с её 29×) — системный вызов быстрее от
  языка не станет.
  ⚠️ Канал RFCOMM ФИКСИРОВАН (`BLUETOOTH_CHANNEL=5` = `kRfcommChannel`) — это
  ровно то же, что порт 5000 у TCP. Константа в двух языках, и тест
  `test_native_layer_agrees_with_python_about_the_channel` держит их вместе:
  разъедься они, узлы слушали бы и звонили на разные каналы и молча никогда не
  встретились. SDP (спросить канал у соседа) НЕ сделан: это ещё сотня строк,
  которую здесь нечем проверить.
  ⚠️ `scan` возвращает ВСЁ видимое — наушники и телефоны тоже. Отсеивает их
  рукопожатие по отпечатку сети, ровно как у UDP-маяка. Поиск соседей общий для
  всех транспортов: `transport.neighbours()` → `node.discover_nearby()`.
  ⚠️ Несобранный C++ ничего не ломает: транспорт работает, теряется только
  автопоиск (`_bridge_json` возвращает {} на любую беду).
  ⚠️ ПЕРЕДАЧА ПО ВОЗДУХУ НЕ ПРОВЕРЕНА: адаптера в контейнере нет
  (`AF_BLUETOOTH` → «Address family not supported»). Проверено всё остальное —
  сборка без предупреждений, векторы C++ (порядок байтов `bdaddr`), поведение
  БЕЗ железа, разбор ответов и логика поиска на подменённом транспорте. Тесты
  с живым адаптером написаны и включатся сами там, где он есть.
  ⚠️ Скорость RFCOMM — сотни КБ/с: блок в 4 МиБ идёт десятки секунд. Это
  запасной путь «роутера нет вообще», а не замена TCP/IP.
  ⚠️ На WINDOWS нативным должен быть ВЕСЬ транспорт (`bhydra_bt_win.cpp`,
  `WindowsBluetoothTransport`): модуль `socket` в CPython не умеет разбирать
  `SOCKADDR_BTH` ни в каком виде, Bluetooth-сокетов там нет. Соединение живёт
  в DLL, Python получает обёртку через ctypes ровно с теми шестью методами,
  которыми пользуется стек (`sendall`/`recv`/`settimeout`/`gettimeout`/
  `shutdown`/`close`). Отдельный файл, а не `#ifdef`: общего кода с BlueZ нет
  вовсе. Транспорт выбирается по системе — `transport.bluetooth_transport()`.
  ⚠️ У ctypes ОБЯЗАТЕЛЬНЫ `argtypes`/`restype`: дескрипторы Winsock 64-битные,
  без этого ctypes обрежет их до int и соединение начнёт читать не оттуда —
  молчаливая порча вместо отказа.
  ⚠️ `bhydra_bt.exe` отвечает тем же JSON, что Linux-слой, поэтому поиск
  соседей — ОБЩИЙ код: `WindowsBluetoothTransport` наследует `scan`/
  `neighbours` без изменений. Канал сверяется тестом сразу в ТРЁХ местах.
  ⚠️ Windows-слой проверен кросс-сборкой mingw-w64 (без предупреждений, PE на
  выходе) и запуском `selftest` ПОД WINE. Wine — не Windows и Bluetooth-стека
  в нём нет: радио и настоящая Windows не проверялись никем.
- **Seed-подключение для КОШЕЛЬКОВ** (`/api/nodes`, `Network.discover`): seed-узлы
  у нас были всегда, но только между УЗЛАМИ (`--seed`, `bootstrap`). Кошелёк
  узлом не является и не станет: в браузере и WebView нет сырых TCP-сокетов,
  нашим кадровым протоколом оттуда не заговорить. Поэтому узел объявляет свой
  REST-адрес соседям (`api`/`api_tls` в `hello` и `peer_api` в ответе `peers`,
  `remember_api`/`api_nodes`), а `GET /api/nodes` отдаёт список кошельку. Телефон
  вводит ОДИН адрес и дальше переживает падение любого узла. Адрес хранится
  рядом с адресами пиров (`peers_file`), поэтому переживает и перезапуск.
  ⚠️ Хост берётся из АДРЕСА ПИРА, а не из тела сообщения, и `peer_api` слушается
  только про тех, кто уже в таблице: иначе один узел уводил бы кошельки на любой
  адрес — то же отравление, от которого закрыт список пиров.
  ⚠️ Свой адрес НИКОГДА не отдаётся как `127.0.0.1` (подставляется `local_ip()`):
  на телефоне loopback — это сам телефон, а в GUI такой хост стоит по умолчанию.
  ⚠️ ОДИН узел под ДВУМЯ адресами (`localhost` и IP в сети) кошелёк считает
  одним: `/api/info` отдаёт `node_id`, `survey()` помечает дубли и исключает их
  из `order()`. Иначе `confirmAcross` врал бы в самую опасную сторону —
  «подтвердили двое», когда узел один, а на числе НЕЗАВИСИМЫХ узлов держится SPV.
  ⚠️ `api.py --p2p` поднимает REST и узел сети в ОДНОМ процессе поверх одной
  цепочки. Без этого REST-узел отвечал бы про свою изолированную копию: телефон
  видел бы одну цепочку, компьютеры — другую. В GUI то же самое — кнопка
  «Кошелёк для телефона» на вкладке «Сеть».
  ⚠️ REST РАССЫЛАЕТ то, что сделал (`_accept_tx`/`_mine` → `p2p.submit_transaction`
  /`p2p.mine`). Раньше звался `node.mine_pending`/`add_transaction` напрямую,
  мимо P2P: блок, добытый через веб-кошелёк, оставался у своего узла, а
  транзакция не доходила до майнеров — снаружи «сеть не работает» при исправном
  соединении. Плюс фоновое обслуживание раз в 15 с (`discover_peers` + `sync`):
  анонсы приносят только то, что произошло ПРИ НАС, и узел, стоявший
  выключенным, иначе так и остался бы на своей высоте.
  ⚠️ `BHydraAPI` хранит узел в АТРИБУТЕ КЛАССА — два REST-сервера в одном
  процессе это ОДИН узел. Поэтому «сеть из двух» в тестах поднимается
  подпроцессами (`_launch_node`), иначе проверка была бы подделкой.
- **Кошелёк синхронизируется с СЕТЬЮ, а не с одним узлом** (`bhydra-net.js`):
  спрашивает `/api/info` у всех известных узлов параллельно и берёт цепочку с
  наибольшей `total_work` — ТО ЖЕ правило, что у `replace_chain`. По высоте
  нельзя: клиент и сеть считали бы главной разные цепочки. Узел с чужим
  генезисом отбрасывается (своя сеть — у большинства ответивших). Запрос при
  отказе узла уходит следующему; 4xx НЕ перебирается — это ответ по существу.
  `/api/info` отдаёт `total_work`, `genesis`, `chain_id` — добавлено ради этого.
  ⚠️ SPV: включение транзакции проверяется путём Меркла против корня из
  ЗАГОЛОВКА блока (`confirm`), а число независимых подтверждений — `confirmAcross`.
  Заголовки на PoW не проверяются, поэтому узел, придумавший блок целиком,
  SPV обманет; защита — несколько независимых узлов и свой собственный.
  ⚠️ Пустой путь Меркла — ОТКАЗ, а не «ноль шагов»: иначе проверка вырождается
  в «лист равен корню», что верно для блока из одной транзакции, и SPV молча
  подтверждает что угодно. Ровно так и было, пока поле читалось как `path`
  вместо `proof`.
  ⚠️ Ключ кошелька СОХРАНЯЕТСЯ (`localStorage`, `bhydra.wallet`) — иначе
  закрытие приложения теряло деньги. Лежит открытым; шифрование под PIN — не
  сделано. Адрес ВЫВОДИТСЯ из ключа: раньше `newWallet()` генерировал две
  независимые случайные строки, и на такой адрес нельзя было потратить деньги
  никогда. Ключ берётся из `crypto.getRandomValues`, не из `Math.random`.
- **Соединения ПОСТОЯННЫЕ** (`send()` + пул `_pool`): сокет после ответа
  возвращается в пул, следующий запрос к тому же пиру идёт по нему. Раньше на
  КАЖДОЕ сообщение открывался новый TCP-сокет — рукопожатие и полный круг
  задержки до первого байта данных. Больнее всего это било по `_sync_from`:
  `get_height` + ~log₂(длины) запросов `get_hashes` + по запросу на пачку
  блоков — десятки соединений подряд к одному соседу. Замер (300 блоков,
  6 пачек): **9 соединений → 1**; на loopback 103 → 95 мс, при эмуляции RTT
  20 мс — 280 → 110 мс (в 2,5 раза быстрее).
  Потолки: `MAX_POOLED_PER_PEER=4`, `MAX_POOLED_CONNECTIONS=64` (дескрипторы).
  ⚠️ `POOL_IDLE_TIMEOUT = INBOUND_TIMEOUT / 2` — СЧИТАЕТСЯ ОТ таймаута сервера,
  не задаётся отдельным числом: держать сокет в пуле дольше, чем сосед готов
  молчать, бессмысленно (он его уже закрыл), а два независимых значения
  разъехались бы. Закреплено `test_pool_idle_timeout_is_derived_from_the_server_timeout`.
  ⚠️ `send()` делает РОВНО ОДИН повтор на свежем соединении: сосед мог закрыть
  idle-сокет по своему таймауту, и без повтора это штатное закрытие выглядело
  бы как «пир недоступен». Повтор безопасен только потому, что повторная
  доставка безвредна (`get_*`/`hello` — чтение, `transaction`/`block`/`inv`
  дедуплицируются получателем). **Неидемпотентное сообщение сюда добавлять
  нельзя** — его выполнят дважды.
  ⚠️ `stop()` рвёт и ПРИНЯТЫЕ соединения (`_conns`): закрытия слушающего сокета
  мало — принятые живут отдельно, и «остановленный» узел продолжал бы отвечать
  всем, кто успел с ним соединиться. Бан тоже рвёт пул (`close_pool(host)`):
  бан, при котором мы разговариваем по открытому сокету, — не бан.
- **Транзакции внутри блока могут быть СВЯЗАННЫМИ**: `_validate_block_transactions`
  ищет вход и в подтверждённом UTXO, и среди выходов ПРЕДЫДУЩИХ транзакций
  этого же блока (порядок обязан быть топологическим, как в Bitcoin). Без
  этого блок со сдачей, потраченной в том же блоке, принимал только сам
  майнер — сеть отвергала штатный блок. Выходы coinbase в этот набор НЕ
  попадают: награду нельзя потратить в блоке, где она создана.
- **Синхронизация ИНКРЕМЕНТАЛЬНАЯ и пачками** (`get_blocks`/`get_hashes`,
  `MAX_BLOCKS_PER_MESSAGE=500`). Прежний `get_chain` отдавал цепочку целиком
  одним сообщением, а лимит сообщения 32 МБ давал сети жёсткий ПОТОЛОК ДЛИНЫ
  (~30 тыс. блоков с одним coinbase, ~10 тыс. с транзакциями) — дальше новый
  узел не смог бы синхронизироваться вовсе. `_sync_from` ищет общий блок
  (двоичный поиск по `get_hashes`, ~log₂ запросов), качает только хвост и при
  простом продолжении применяет блоки по одному через `receive_block` —
  проверяется лишь новое, поверх уже проверенного префикса. Догон одного блока:
  1,5 КБ вместо всей цепочки. Реорг идёт через `replace_chain` (по работе).
  `MAX_SYNC_BLOCKS=100000` ограничивает одну докачку — очень длинную цепочку
  узел догоняет за несколько вызовов `sync()`.
  ⚠️ Пачка ограничена И ПО РАЗМЕРУ (`MAX_BATCH_BYTES = MAX_MESSAGE_SIZE // 4`),
  а не только по числу блоков: блок вмещает до 5000 транзакций (~3,8 МБ),
  поэтому 500 таких блоков — около 1,9 ГБ, сообщение сверх лимита получатель
  отбрасывает, и синхронизация встаёт. Бюджет считается ОТ лимита сообщения,
  чтобы два числа не разъехались. Один блок отдаётся всегда, даже если он
  больше бюджета, — иначе цепочку с крупным блоком не догнать вовсе.
  ⚠️ Потолок блока в байтах — `MAX_BLOCK_SIZE=4` МиБ, и он СВЯЗАН с
  транспортом: `MAX_MESSAGE_SIZE = 8 × MAX_BLOCK_SIZE`. Менять поодиночке
  нельзя — поднять потолок блока без лимита сообщения значит сделать часть
  валидных блоков непередаваемыми. Соотношение закреплено тестом
  `test_block_size_fits_the_transport`, сама величина — `test_block_size_limit_is_pinned`.
- **`seen_blocks` помечается ПОСЛЕ разбора, а не до**: блок «из будущего»
  (`index > height` — мы просто отстали) виденным не считается, поэтому его
  повторная рассылка даёт ещё одну попытку догнать. Брак и чужие развилки
  помечаются сразу — их дорогая проверка выполняется один раз. Докачка
  цепочки по чужому блоку throttled (`sync_retry_interval=2` с), чтобы пир не
  гонял нас за полной цепочкой без ограничений.

## Соглашения

- Разработка на ветке `claude/*` (для сессии её задаёт задание), PR в `main`;
  напрямую в `main` не пушить.
- **Дерево Меркла** — единая реализация в `merkle.py` (её же использует
  `blockchain.py`; корень байт-в-байт как раньше). Умеет доказательства
  включения (SPV): `merkle_proof`/`verify_proof`, `node.merkle_proof(txid)`,
  REST `GET /api/proof/<txid>`. CVE-2012-2459 закрыт запретом дублей txid в
  блоке (`has_duplicate_promotion` помечает дерево с дублированием).
- **Файл состояния пишется АТОМАРНО** (`node.save`: временный файл + fsync +
  `os.replace`). Прежний код открывал целевой файл на `"w"`, то есть ОБРЕЗАЛ его
  сразу, и только потом писал: любой обрыв посреди записи оставлял наполовину
  записанный JSON. Это не теория — у пользователя клиент падал при КАЖДОМ
  запуске с `JSONDecodeError: Expecting ',' delimiter: line 3992 column 153
  (char 185473)`, окно не открывалось вовсе, и починить это из интерфейса было
  нечем. Тот же приём давно применён к таблице пиров и ключу узла (`p2p.py`) —
  до состояния цепочки просто не дошли руки.
  ⚠️ Однажды испорченный файл сам не выздоровеет, поэтому запуск обязан его
  ПЕРЕЖИВАТЬ: `BHydraNode.open_state` возвращает `(узел, сообщение)` и идёт по
  цепочке «прочитать целиком → спасти уцелевшее начало (`recover`) → начать
  заново». Оборванная запись рвёт файл посреди массива блоков, но всё до
  разрыва — целые JSON-объекты: они вычитываются по одному, и владелец теряет
  последние блоки, а не весь кошелёк.
  ⚠️ Спасённая цепочка ОБЯЗАНА пройти `is_chain_valid()`: хвост отрезается,
  пока не сойдётся. Последний дочитанный блок бывает синтаксически целым, но
  ссылается на то, чего в файле не осталось, — принять такой значит завести
  узел с невалидным состоянием, что хуже, чем не открыться.
  ⚠️ Битый файл НЕ удаляется, а откладывается как `<файл>.corrupt-<время>`:
  решать его судьбу вправе только владелец монет.
  ⚠️ `load()` звали НАПРЯМУЮ все три точки входа — GUI, REST и CLI, — и падали
  все три. Поэтому `open_state` живёт в `node.py`, а не в `gui.py`.
  ⚠️ В `recover` сложность читается из уцелевшего заголовка, и это важно:
  `json.raw_decode` НЕ пропускает пробелы, поэтому наивное чтение с позиции
  после двоеточия падало, подставлялось умолчание, и вся цепочка потом не
  проходила проверку — спасался один генезис вместо всех блоков.
- **Обход дерева XMSS — BDS** (`pqcrypto.py`, `_Treehash`). Листья НЕ ХРАНЯТСЯ:
  секретный ключ WOTS выводится из `seed || i`, лист считается по требованию, а
  путь включения строится инкрементально (Buchmann–Dahmen–Szydlo, приём из
  RFC 8391). Прежняя реализация держала все 2^h ключей и звала `merkle_proof` по
  ВСЕМ листьям на КАЖДОЙ подписи. Замер: состояние при h=8 1275 КБ → 4 КБ (и
  больше не растёт с деревом вовсе), хешей узлов на подпись 2^h−1 → ≈0,65·h
  (63 → 2,7 при h=6; 1023 → 6,5 при h=10).
  ⚠️ ГЕНЕРАЦИЯ ОСТАЛАСЬ O(2^h), и это неустранимо: публичный ключ ЕСТЬ корень
  над всеми 2^h листьями, значит каждый лист обязан быть посчитан хотя бы раз.
  Обход касается ПОДПИСЕЙ, а не генерации. Замер листа: 227 мс на чистом SHA,
  1,0 мс на быстром бэкенде → h=8 58 с, h=12 15 мин, h=16 4,1 ч, h=20 66 ч.
  Потолок высоты теперь задаёт ОДНО ожидание при создании кошелька, а не память.
  ⚠️ Корень и формат пути НЕ ИЗМЕНИЛИСЬ — это правило сети: корень входит в
  гибридный адрес, подписи проверяют узлы. Сверено с наивным эталоном на КАЖДОМ
  индексе деревьев h=1..8 и обоих наборах параметров, `MerkleSigner.verify` не
  тронут вовсе.
  ⚠️ `from_dict` передаёт индекс В КОНСТРУКТОР, а не присваивает после. Раньше
  присваивания хватало (дерево строилось целиком), теперь путь — часть
  состояния обхода, и `signer.index = k` задним числом оставил бы путь от
  нулевого листа. Формат `bhydra_hybrid.json` не изменился: состояние обхода
  не сохраняется, оно выводится из (seed, height, index) одним проходом —
  восстановление стоит ровно столько же, сколько генерация (замер: отношение
  1,01). Наивное «проиграть все подписи от 0 до index» стоило бы для h=16 и
  index=50 000 в шесть раз дороже полной генерации.
- **Пост-квантовая крипта** (`pqcrypto.py`, экспериментально, НЕ в консенсусе):
  хеш-подписи на нашем SHA — Lamport (OTS), WOTS (Winternitz OTS + контрольная
  сумма), XMSS-lite (дерево Меркла над WOTS-ключами → многоразовая подпись,
  переиспользует `merkle.py`), `QuantumWallet` (адрес `BHYQ…`). Квантово-
  устойчивы: Шор ломает ECDSA, но не хеши; Гровер лишь вдвое ослабляет.
  Два режима (оба наших хеша): `P256` (элементы SHA-256, 128 бит, по умолчанию,
  компактно) и `P512`/`strong=True` (SHA-512, 256 бит даже после Гровера).
  Подписи с СОСТОЯНИЕМ (ключ WOTS одноразовый).
- **Гибридные квантово-защищённые кошельки** (`HybridWallet`, В КОНСЕНСУСЕ):
  адрес версии `0x2f` (тоже `BHY…`) привязан к ДВУМ ключам — ECDSA + XMSS-корню
  (`hybrid_address`, `is_hybrid_address`). Трата требует ОБЕ подписи
  (`tx.sign_hybrid`, `node.create_hybrid_transaction`); узел проверяет их в
  `_verify_input_auth` и ведёт учёт израсходованных одноразовых XMSS-ключей
  (`node.pq_used_indices`, накопитель `pq_used` в `validate_transaction` /
  `mine_pending` / `_validate_block_transactions` / `_validate_chain`).
  Квант ломает лишь ECDSA — монеты на гибридном адресе недоступны. Обычные
  ECDSA-кошельки (`0x1f`) работают как раньше (обратная совместимость).
- **Перед push — `python -m pytest -q` должно быть зелёным** (903 + 2 пропуска без адаптера Bluetooth; без IPv6 в системе пропускаются ещё 2 теста; без устройства OpenCL пропускаются ещё 23 теста GPU-майнера, без скачанных android.jar/dx.jar — ещё 5 тестов сборки APK).
- Коммиты по-русски, осмысленные; заканчиваются трейлерами
  `Co-Authored-By:` и `Claude-Session:`.
- Не хардкодить идентификатор модели в коде/коммитах/артефактах.

## Состояние и направления

Сделано (PR #1–#4 влиты в `main`): чинка багов ядра, мемпул на 10k+, живой
веб-обозреватель и кошелёк, настоящие переводы через узел с понятными ошибками,
нативный ECDSA-ускоритель, смарт-контракты на цепочке (эскроу + смарт-чеки,
REST-эндпоинты `/api/contract/...`).

Дальше (по приоритету пользователя — «сначала скорость, потом DAG»):
1. скорость — сделано: ECDSA-ускоритель, инкрементальный кэш UTXO
   (`utxo_set` применяет только новые блоки, реорг → пересборка; попутно
   tx-индекс O(1) и PQ-учёт цепочки) и LRU-кэш проверенных подписей
   (`_verify_ecdsa_cached`: мемпул→блок→прунинг не перепроверяют ECDSA;
   mine_pending со 100 tx: 1364→8 мс). Параллелизм не делаем: GIL не даёт
   выигрыша чистому Python, а нативный путь уже покрыт coincurve;
2. **blockDAG** (GHOSTDAG-lite) — СДЕЛАНО как отдельный модуль `blockdag.py`
   (не трогает линейную цепочку): блок ссылается на все вершины-tips (много
   родителей), k-кластерная раскраска синий/красный, blue_score вместо высоты,
   тотальный порядок. Плюс **гибрид** `HybridDagChain`: блоки накапливаются в
   DAG, а PoW-нонс (`Checkpoint.mine`) финализирует их в линейную контрольную
   точку и схлопывает DAG (новый якорь — хеш точки). Цепочка точек = линейный
   PoW-блокчейн из DAG-пачек. Улучшает блоки/с, крипту не ускоряет. Дальше:
   привязать реальные UTXO-транзакции и дедуп по синему набору.
3. настоящая браузерная подпись — СДЕЛАНО: `bhydra-sign.js` (SHA-512, HMAC,
   RIPEMD-160, base58, secp256k1, RFC 6979 и сериализация «как в Python» —
   без зависимостей). Кошелёк подписывает на устройстве и шлёт готовую
   транзакцию в `POST /api/transaction`; приватный ключ на узел не уходит.

Отдельно сделано по безопасности:
