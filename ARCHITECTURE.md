# Архитектура B-hydra

Одноранговая электронная денежная система (P2P electronic cash) на собственной
криптографии. Этот документ — карта всей системы: слои, модель данных,
консенсус, сеть и модель безопасности.

---

## 1. Слои (пакет `b_hydra/`)

Каждый слой опирается только на нижние — снизу вверх:

```
┌───────────────────────────────────────────────────────────────┐
│  Точки входа:  manig.py · cli.py · api.py · P2P.py · mobile_client.py │
├───────────────────────────────────────────────────────────────┤
│  api.py            REST API + веб-обозреватель (explorer.html)   │
│  p2p.py · tcp.py   P2P-сеть: gossip, синхронизация, транспорт    │
├───────────────────────────────────────────────────────────────┤
│  node.py           Узел: UTXO-набор, мемпул, майнинг, валидация  │
├───────────────────────────────────────────────────────────────┤
│  blockchain.py     Блоки, PoW, динамическая сложность, работа    │
│  economics.py      Награда, халвинг, конец эмиссии (3000)        │
│  transaction.py    UTXO-транзакции (входы/выходы), мемпул        │
│  contract.py       Смарт-контракт и эскроу                       │
├───────────────────────────────────────────────────────────────┤
│  wallet.py         Ключи ECDSA secp256k1, адреса, подпись        │
│  merkle.py         Дерево Меркла (двойной SHA-512)               │
│  hashcash.py       Proof-of-work примитив                        │
├───────────────────────────────────────────────────────────────┤
│  hashing.py        Переключаемый движок SHA (pure ⇄ hashlib)     │
│  sha2.py           SHA-256/512 «с нуля» (FIPS 180-4)             │
└───────────────────────────────────────────────────────────────┘
```

**Поток зависимостей:** `sha2 → hashing → {merkle, wallet, transaction,
blockchain, hashcash} → node → {p2p, api}`.

## 2. Хеширование — переключаемый движок

Весь SHA в проекте идёт через `hashing.py`. Движок по умолчанию — **наша
реализация «с нуля»** (`sha2.py`), но хеши побитово равны `hashlib`, поэтому
переключение не влияет на консенсус:

```
            ┌── BHYDRA_PURE_SHA=1 (по умолчанию) → sha2.py   (свой код)
hashing.sha512(x) ──┤
            └── BHYDRA_PURE_SHA=0                → hashlib    (быстро)
```

## 3. Модель данных

### Кошелёк (wallet.py)
```
приватный ключ ──(× G на secp256k1)──▶ публичный ключ ──(хеш)──▶ адрес
   256-бит секрет        ECDSA            04||X||Y         "BHY"+Base58
```
- Адрес = `BHY` + Base58( `0x1f` || RIPEMD160(SHA-512(pub)) || checksum ).
- Подпись: ECDSA secp256k1 над SHA-512 сообщения, формат `r||s` (low-s).

### Транзакция UTXO (transaction.py)
Как в Bitcoin — входы тратят прошлые выходы, выходы блокируются на адрес:
```
Transaction
 ├─ vin:  [ TxInput(txid, index, public_key, signature), … ]   ← ссылки на UTXO
 ├─ vout: [ TxOutput(amount, address), … ]                     ← новые выходы
 └─ txid = SHA-512(chain_id + vin-outpoints + vout + timestamp)
            (chain_id вшит в подпись → защита от replay между сетями)

coinbase: один вход «ниоткуда» (NULL_TXID), без подписи — награда майнеру.
```

### Блок (blockchain.py)
```
Block
 ├─ index, previous_hash, timestamp, nonce, difficulty
 ├─ merkle_root = корень Меркла транзакций (двойной SHA-512)
 ├─ data        = [coinbase, tx, tx, …]   (только адреса и суммы)
 └─ hash = SHA-512(index || prev || merkle || timestamp || difficulty || nonce)
```
`difficulty` входит в хеш — её нельзя занизить задним числом.

### Цепочка
```
[Генезис]──prev──[#1]──prev──[#2]──prev──[#3]── …
 (общий для всех узлов, фиксированный timestamp)
```

## 4. Консенсус

- **PoW (как Bitcoin):** майнер перебирает `nonce`, пока хеш как число не станет
  `≤ target` (порог). Меньше target → пропорционально труднее.
- **Ретаргетинг сложности по времени (как Bitcoin):** каждые `RETARGET_INTERVAL`
  блоков цель пересчитывается (`expected_target`) по фактическому времени окна
  относительно ожидаемого (`interval × TARGET_BLOCK_TIME`): быстрее цели → target
  уменьшается (труднее), медленнее → увеличивается (проще), но не более чем в
  `MAX_ADJUST_FACTOR` (×4) за пересчёт и не легче генезиса. Целочисленно и
  детерминировано из меток времени → проверяет каждый узел. Больше майнеров →
  блоки идут быстрее цели → следующий пересчёт поднимает сложность (то же
  «больше майнеров — труднее», но как естественное следствие, как в Bitcoin).
- **Выбор главной цепочки:** по **суммарной работе** `Σ (2^512 / target)`
  (`total_work`), а не по длине — длинная цепочка дешёвых блоков не победит.

```
Майнинг блока:
  собрать tx из мемпула → coinbase(награда+комиссии)
        → подобрать nonce (PoW) → добавить в цепочку → разослать сети
```

## 6. P2P-сеть (p2p.py + tcp.py)

### Транспорт
JSON-сообщения поверх TCP с 4-байтовым префиксом длины (лимит 32 МиБ = 8 ×
`MAX_BLOCK_SIZE`), **в зашифрованном канале** (`secure.py`): эфемерный ECDH на
secp256k1 → поток SHAKE-256 + HMAC-SHA512 (Encrypt-then-MAC), номера кадров
против повторов и выбрасывания. Узел подписывает рукопожатие своим
долговременным ключом, клиент закрепляет его при первом контакте (TOFU).
У транспорта есть вторая, нативная реализация — `cpp/` (тот же протокол
байт-в-байт, рукопожатие в 29 раз быстрее; см. `cpp/README.md`).
Соединения **постоянные**: сокет после ответа возвращается в
пул и переиспользуется для следующего запроса к тому же пиру (`MAX_POOLED_*`),
а сервер читает из одного соединения сколько угодно сообщений подряд. Идёт
ровно один повтор на свежем сокете — сосед мог закрыть idle-соединение по
своему таймауту (`POOL_IDLE_TIMEOUT = INBOUND_TIMEOUT / 2`).

### Протокол сообщений
```
ping                   → pong
hello{host,port,api,chain_id,genesis} → peers[…]  (знакомство + опознание сети)
get_peers              → peers[…,peer_api,api]    (не больше 32 адресов)
get_height             → height{height, work}  (work — правило консенсуса)
get_hashes{from,count} → hashes[…]             (поиск развилки, дёшево)
get_blocks{from,count} → blocks[…]             (пачка: ≤500 шт и ≤8 МиБ)
inv{kind,hash,from}    → ack{wanted}           (АНОНС блока или транзакции)
get_block{hash}        → block_body
get_tx{txid}           → tx_body
block{block, from}     → ack{accepted,height}
transaction{tx, from}  → ack{accepted}
```

### Gossip — распространение по всей сети (multi-hop)
Узел анонсирует **новый** блок/транзакцию остальным соседям (кроме источника),
с дедупликацией (`seen_blocks`, `seen_tx`) против петель. Уходит только ХЕШ —
тело сосед забирает сам, и лишь если его у него нет:

```
A майнит блок
A ──inv(hash)──▶ B ──inv──▶ C ──inv──▶ D
   ◀─get_block──    (B переслал)  (C переслал)
   ──block_body─▶  даже если A и D НЕ соединены напрямую — блок дойдёт.
```

### Как в сеть попадает КОШЕЛЁК (телефон, браузер)
Кошелёк узлом не является: в браузере и в `WebView` нет сырых TCP-сокетов, и
нашим кадровым протоколом оттуда не заговорить. Он HTTP-клиент, и ему нужна
точка входа — как список серверов у Electrum, а не DNS-сиды Bitcoin Core.

Поэтому узел объявляет соседям ещё и свой **REST-адрес** (`api` в `hello`,
`peer_api` в ответе `peers`), а `GET /api/nodes` отдаёт этот список кошельку:

```
телефон ──вписал ОДИН адрес──▶ узел A ──/api/nodes──▶ [A, B, C]
   └── дальше сам: выбор по total_work, отказ A ⇒ работает через B
```

Это и есть seed для кошелька. Адреса хранятся рядом с адресами пиров, поэтому
переживают перезапуск. `python -m b_hydra.api --p2p` поднимает REST и узел сети
в одном процессе поверх ОДНОЙ цепочки — иначе телефон видел бы одну цепочку,
а компьютеры другую.

### Синхронизация
Новый/отставший узел подтягивает цепочку с наибольшей работой —
инкрементально, а не целиком:
```
node.sync():  у кого больше WORK? (пробуем до 4 кандидатов)
              → get_hashes: двоичный поиск общего блока (~log₂ запросов)
              → get_blocks: только хвост, пачками
              → продолжение: receive_block по одному
                развилка:    replace_chain (полная проверка, решает work)
```

## 7. Модель безопасности

### Что защищено кодом ✅
| Угроза                                   | Защита                          |
|------------------------------------------|---------------------------------|
| Трата чужих средств                      | ECDSA-подпись + адрес из ключа  |
| Двойная трата / перерасход / подмена суммы | проверка UTXO в блоке/мемпуле  |
| Фальшивый coinbase (печать монет)        | `coinbase ≤ награда + комиссии` |
| Подделка транзакций в чужой цепочке      | полная ревалидация `_validate_chain` |
| Длинная цепочка дешёвых блоков           | консенсус по работе `total_work`|
| Подмена данных блока                     | корень Меркла в хеше            |
| Занижение сложности                      | difficulty в заголовке/хеше     |
| Чужая сеть                               | общий генезис                   |
| Манипуляции временем                     | будущее (+2ч) / ход назад       |
| Replay между сетями/форками              | chain_id в подписи транзакции   |
| XSS в обозревателе                       | экранирование + data-атрибуты, валидация адреса |
| Invalid-curve публичный ключ             | проверка точки на кривой в verify() и в ECDH |
| DoS по памяти                            | лимиты сообщения/тела/блока     |
| Прослушка канала (провайдер, WiFi)       | шифрование транспорта (ECDH + SHAKE-256) |
| Прослушка REST/браузера                  | настоящий TLS 1.2+ (`--tls`, stdlib `ssl`) |
| Приватный ключ по открытому HTTP         | 403 вне TLS и вне локального адреса |
| Один лгущий узел для кошелька            | выбор по работе + SPV-путь Меркла + сверка у нескольких узлов |
| Потеря ключа при очистке хранилища (iOS) | выгрузка ключа в файл + напоминание, пока копии нет |
| Подмена кадра в пути                     | HMAC-SHA512 Encrypt-then-MAC    |
| Повтор/выбрасывание/перестановка кадров  | порядковые номера кадров        |
| Понижение до открытого канала            | отката нет — отказ соединения   |
| Подмена узла на знакомом адресе          | подпись рукопожатия + TOFU-закрепление |
| Утечка старых сессий при краже ключа узла| эфемерный ECDH (прямая секретность) |

### Что НЕ лечится кодом ⚠️
- **51%-атака** — свойство PoW: нужна честная вычислительная мощность больше,
  чем у атакующего. На чистом Python хешрейт низкий — это учебная сеть.
- **Посредник при ПЕРВОМ контакте** с новым пиром: доверие берётся из первого
  соединения (TOFU, как в SSH), поэтому подмена ключа именно в этот момент
  незаметна. Со второго раза она видна. Полное лечение потребовало бы PKI или
  сверки ключей вне канала.
- **Аутентификация клиента**: входящее соединение не доказывает, кто на другом
  конце, — у него всё равно виден только IP, по нему и считается репутация.

## 8. Точки входа

```
python manig.py          полный демо-цикл (кошельки → майнинг → перевод)
python cli.py …          CLI: wallet / init / mine / send / balance / chain
python api.py            REST API + обозреватель  http://<IP>:8000/
python P2P.py --port …   узел распределённой сети (--peer host:port)
python mobile_client.py  эталонный мобильный кошелёк (подпись на устройстве)
pytest                   автотесты
```

### Полный узел в сети
```
        ┌──────────── узел B-hydra ────────────┐
HTTP ──▶ api.py ──▶ BHydraNode ◀── p2p.py ◀── TCP (другие узлы)
браузер │           (blockchain,                │
телефон │            UTXO, мемпул)              │
        └──────────────────────────────────────┘
```
